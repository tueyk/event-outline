## 1. 技术底座

VPS 上酒馆是 **SillyTavern 1.19.0**，容器 `sillytavern`，镜像 `ghcr.io/sillytavern/sillytavern:1.19.0`。

`/opt/tavern/extensions` 挂到容器内 `public/scripts/extensions/third-party`。

已装扩展（6 个）：JS-Slash-Runner 4.11.3、ST-BaiBai-Book、ST-Prompt-Template、SillyTavern-Pathweaver、scene-map（已禁用）、shujuku 1.3。

前端扩展只需 `manifest.json` + `index.js`，不重启容器，硬刷生效，删目录即回滚。

### 1.1 可用 API（来自 `public/scripts/st-context.js` 的 `getContext()`）

| 用途 | API |
|---|---|
| 读聊天 | `ctx.chat`、`ctx.chatId` |
| 读/存 chat metadata | `ctx.chatMetadata`、`ctx.saveMetadata()`、`ctx.saveMetadataDebounced()` |
| 触发生成 | `ctx.generateRaw({prompt, systemPrompt, jsonSchema, responseLength})`、`ctx.generateQuietPrompt(...)` |
| Token 计数 | `ctx.getTokenCountAsync(text)` |
| 上下文上限 | `ctx.getMaxPromptTokens()` |
| 请求头（含 CSRF） | `ctx.getRequestHeaders()` |
| 世界书读写 | `fetch('/api/worldinfo/get'/'edit')` + `getRequestHeaders()` |
| 事件 | `ctx.eventSource.on(ctx.eventTypes.CHAT_CHANGED / MESSAGE_RECEIVED, fn)` |
| 设置持久化 | `ctx.saveSettingsDebounced()`、`ctx.extensionSettings` |

### 1.2 三个不可用的方向（已实测排除）

| 方向 | 为什么不行 |
|---|---|
| `is_system` 隐藏楼层 | `script.js:4496` `coreChat = chat.filter(x => !x.is_system)`，**模型看不到**，方向相反 |
| 靠世界书自动注入 | `generateRawData` 不调用 `getWorldInfoPrompt`，蓝灯对静默生成无效 |
| `setExtensionPrompt` 注入 | 只影响正常生成链路，对 `generateRaw` 无效 |

结论：**必须自己拼上下文**。参照实现见 §3.2。

### 2.2 世界书条目

前缀统一 `▸事件｜`，写在角色主世界书（`characters[chid].data.extensions.world`）。

**生成与写入分离**（2026-10-31）：

生成不再直接写世界书。`createEvent` 只产出 `status: 'draft'` 的事件卡，
存在 `chat_metadata.event_outline.events` 里，最多同时保留 `MAX_DRAFTS = 3` 个，
超出时挤掉 `createdAt` 最早的那个。

| 时机 | 世界书 | currentEventId |
|---|---|---|
| 生成（`createEvent`） | 不写 | 不改 |
| 采用（`commitDraft`） | 写条目 | 改 |
| 丢弃（`discardDraft`） | 不涉及 | 不改 |
| 废弃/完结（`closeEvent`） | 删条目 | 清空 |

`commitDraft` 要求当前没有进行中的事件，否则报错让用户先收掉旧的
——这样不会出现两个 active 抢同一条世界书条目的情况。
待选区不写世界书，所以反复重生成只是改数据，不会来回写删条目。

## 3. 核心流程

### 3.1 生成大纲

```
用户点「开新事件」
  → 填事件名 + 选偏好 + 额外要求
  → buildOutlinePrompt(prefs)          // OOC 改良词 + 偏好替换
  → gatherContext()                    // 事件卡无，只需最近楼层
  → generateRaw({ prompt, systemPrompt })
  → parseOutline(raw)                  // 宽松解析
  → 存事件卡（status=active）
  → writeWorldEntry()                  // 蓝灯条目
  → 面板展示
```

### 3.2 上下文拼装（关键）

只有一条路：自己拼。参照酒馆自带 memory 扩展（`public/scripts/extensions/memory/index.js`）的做法。

它的核心逻辑（第 761 行 `getRawSummaryPrompt`）：

```js
const PROMPT_SIZE = await getMaxPromptTokens();
for (let index ...) {
    const entry = `${message.name}:\n${message.mes}`;
    chatBuffer.push(entry);
    const tokens = await countSourceTokens(getMemoryString(true), PADDING);
    if (tokens > PROMPT_SIZE) { chatBuffer.pop(); break; }
}
```

我们的实现分三层。第二层走 §4.1 的适配器选择（默认自动），第三层永远兜底：

```
第零层（必带，可在设置关闭）：角色世界书的常驻条目
  - generateRaw 不调用 getWorldInfoPrompt，蓝灯对静默生成无效（§1.2），只能自己读
  - 走 POST /api/worldinfo/get 读 bookName 对应的整本，只取 constant: true 且未 disable 的条目
  - 剔除四类：TavernDB-ACU-*（shujuku 导出副本，扩展已单独读表）、
    [mvu_update]* 与「变量列表」（只服务主对话 MVU，不产生剧情设定）、
    ▸事件｜*（本扩展自己写的条目，拼进去会自我循环）、
    含 <% 的 EJS 条件模板（原文里所有分支都在，直接拼会让模型看到没生效的分支）
  - 按 order 升序拼接，超过 worldbook.maxChars（默认 30000 字，0 不限）按序截断
  - 实测「异常应对女子高中」：36 条蓝灯 → 保留 11 条共 1 万字，剔除 25 条

第一层（必带）：事件卡状态
  - 当前大纲摘要
  - tracker：已触发节点、未触发节点、已推翻误导

第二层（按设置选适配器，默认自动探测）：记忆/纪要召回
  - 探测到 shujuku 纪要表时，内部按当前填表模式自动选召回策略：
      shujuku 是 llm 模式：
        取「概览」列全部列出（30字×204≈6000字）
        → 让模型点名精读哪几条 → 取被点名条目的「纪要」正文（240-480字×N）
      其余模式（classic/vector/crossfire，或模式读不到）：
        直接取最近 jiyaoRecentRows 条纪要正文（默认 30 条），零额外调用
  - 没探测到任何记忆模块：本层为空，不影响后续

第三层（永远可用）：最近楼层原文
  - 最近 15 楼（可配），跳过 is_system 和空 mes
  - 补上纪要表尚未覆盖的最新剧情
  - 也是第二层完全不可用时的唯一来源

拼装顺序（某层为空就跳过那段，不留空标题）：
  system: 大纲/盘点指令
  user:   [世界观设定] → [事件状态卡] → [纪要概览 → 纪要正文] → [最近剧情] → 实际问题
```

**生成大纲也走同一套上下文**。早期版本生成大纲时只发指令文本，模型看不到任何剧情与设定，只能凭空编；现在 `createEvent` 先 `gatherContext(null)` 再拼 prompt，与盘点共用同一份上下文。

### 3.2.1 生成进度

一次生成要串好几步，耗时从几毫秒到几十秒不等，只显示「生成中」用户无法判断是否卡死。`startProgress(title)` 建一个步骤列表，`step(text)` 每推进一步就刷新面板：

```
读取角色世界书 → 世界书已载入：N 条常驻设定，M 字
读取 shujuku 纪要 → 纪要：经典表格模式，带入最近 N 条正文（共 M 条）
读取最近 15 楼 → 最近剧情已载入：N 字
请求模型（「配置名」，输入约 N 千字）   ← 停在这一步时每秒刷新「已用时 N 秒」
模型已返回 N 字
解析模型返回的大纲 → 解析完成：N 个信息节点
```

已完成步骤打勾并显示耗时，未完成的显示 ⋯。结束时 `setBusy(false, true)` 保留列表 4 秒后变淡，让用户看清各步花了多久。

### 3.3 盘点

```
用户点「盘点」
  → 需要 status=active 的事件卡
  → gatherContext()（三层全用）
  → buildInventoryPrompt()
  → generateRaw({ prompt, systemPrompt })
  → parseInventory(raw)
  → 结果存 inventories[]
  → 按 tracker 模式处理打勾
  → writeWorldEntry()（覆盖更新同一条）
  → 面板展示
```

### 3.4 tracker 三档
| 模式 | 行为 |
|---|---|
| `auto`（默认） | 模型判定 → 直接写 tracker → 记 `autoCommitted` → 更新世界书 |
| `semi` | 模型判定 → 面板高亮待确认 → 确认后写入 |
| `manual` | 模型只出报告 → 全部手动勾 |

约束：
- 三档都只把**已确认部分**写进世界书
- `nodeVetoed` 里的节点，auto 模式不再自动勾
- 每次自动勾选留痕（`autoCommitted`）

### 3.5 收尾

```
点「收尾」→ 选 完结 / 废弃
  → 定位世界书 `▸事件｜` 条目（现查位置，不盲信 entryUid）
  → 删掉该条目
  → status 改 completed / abandoned，写 closedAt
  → 按 retention 清理超限历史卡
```

### 3.6 条目位置自愈

`entryUid` 记的是「条目当时在哪」，不是「条目永远是这条」。
世界书整本 JSON 是别的插件也能重写的，shujuku 这类导入器会重排 uid，
一旦重排，我们记的编号就指到别人身上去了。

2026-10-31 真实发生过：事件「末潮回抽」记的 uid=49，之后 49 变成
shujuku 的纪要条目「TavernDB-ACU-CustomExport-纪要-包裹-下」，真正的大纲被挤到 51。
如果照旧号写入或删除，改的就是别人那条。

所以写入、删除、收尾三处都不直接用 `entryUid`，而是先调 `findEventEntryUid()`
在已读出的世界书数据里重新定位。查找按可信度依次降级：

| 顺序 | 依据 | 适用情况 |
|---|---|---|
| 1 | 记下的 uid 还在，且注释的前缀、名字、chatId 三者都对 | 正常情况，一次命中 |
| 2 | 注释里 chatId + 事件名都对 | uid 被重排过 |
| 3 | 注释里 chatId 对得上，且只有一条 | 事件改过名 |
| 4 | 注释里没有 chatId，且名字唯一 | 最早的条目格式，只写 `▸事件｜名字` |

第 3、4 步都要求「恰好一条」，多条一律返回 null 不乱猜——
宁可报找不到，也不能删错别人的条目。

定位结果与记录的编号不一致时，写一条 `warn`，说明从哪个 uid 纠正到哪个，
再把新位置写回事件卡。另外切换对话和打开面板时各跑一次 `healEntryUids()`，
把事件卡里的编号批量纠正过来，只改本地事件卡，不动世界书内容。

条目注释格式因此定为 `▸事件｜<事件名>｜chatId=<对话名>`，
名字与 chatId 都参与定位，缺一不可。

### 3.7 世界书读写（高风险，必须严谨）

接口：`POST /api/worldinfo/get`（读）、`POST /api/worldinfo/edit`（写）。

**服务端实现**（`src/endpoints/worldinfo.js:134`）：

```js
if (!('entries' in request.body.data)) throw ...
writeFileAtomicSync(pathToWorldInfo, JSON.stringify(request.body.data, null, 4));
```

要点：
- **没有增量接口**，必须整本读-改-写
- 原子写入，不会写一半崩掉

**实测安全性**（伊瑟利亚3.7：571 条 / 2.7MB / 127 个 EJS 条目）：
- 原始 2,737,968 字节，`JSON.stringify(data, null, 4)` 后**字节完全相同**
- EJS 条目数不变
- uid 0–570 连续无断档

**必做防护**：

| 措施 | 实现 |
|---|---|
| 全局写锁 | 模块级 Promise 队列，同一时刻只一个写操作 |
| 只增不改 | 只追加 `▸事件｜` 前缀新条目 |
| 写前快照 | 整本 JSON 存 `chatMetadata.event_outline.snapshots` |
| 写后校验 | 回读比对，规则见下 |
| 失败中止 | 校验不一致立即中止并提示，不重试 |
| 删除只删自己 | 只删 `▸事件｜` 前缀且 uid 匹配 |

**写后校验的准确规则**（因为 shujuku 会并发改动这本书，不能简单用"条目数只增不减"）：

```
1. 收集写入前所有非 ▸事件｜ 前缀的条目，建 {uid: hash(content + 关键字段)}
2. 回读后重新收集，逐个比对
3. 通过条件：
   - 所有写入前存在的非 ▸事件｜ 条目，内容与关键字段未变
   - 我们新增的 ▸事件｜ 条目确实存在
4. 任一不满足 → 中止，提示「世界书被其他进程同时修改」
```

**为什么不用条目数判断**：shujuku 在向量/交火模式下会动态增删 `TavernDB-ACU-CustomExport-` 前缀的条目（实测伊瑟利亚3.7 里有 227 条）。如果它在我们写入的间隙改了一次，条目总数就会变，用"总数只增不减"会误报失败。

正确做法是**只看内容哈希**，不看总数。这样 shujuku 怎么增删它自己的条目都不影响我们判断。

**为什么这仍然安全**：我们只比对非 `▸事件｜` 前缀条目的内容。shujuku 动的是它自己的前缀，哈希对不上才说明真的出问题。

**关于 ignoreBudget**：不需要。预算公式是 `budget = Math.round(world_info_budget × maxContext / 100)`，`world_info_budget` 默认 25，`maxContext` 取 `getMaxPromptTokens()`，走 `openai_max_context = 2,000,000`，所以预算约 49.25 万 token。

现有 48 条蓝灯（17.3 万字符）仅占约 10.8 万 token，余量 38.4 万。加 ignoreBudget 反而让条目脱离预算管理，以后调小预算时它不跟着缩。

补充：`max_context`（旧字段）是 8192 但**不生效**，不要拿它算预算。

## 5. 界面

### 5.1 悬浮窗

几何实现参照预设「Izumi 1002」内嵌的 TavernHelper 脚本「泉此方悬浮窗」（webpack 打包，含 `src/core/edge-dock.mjs`）。取它而不是自己写，是因为它已经踩平了移动端的坑。

**状态结构**

```js
// extension_settings.event_outline.ui.floatingPos
{ anchor: { x, y }, dock: 'left' | 'right' | null }
```

`anchor` 始终是**展开后图标**的左上角坐标；`dock` 只表示是否吸附、吸附在哪侧。两者分开存，拖动时才能算对偏移量。早期版本把 `side` 和位置混在一起，导致拖不到任意位置，这是被实测推翻的写法。

**尺寸常量**

| 常量 | 值 | 说明 |
|---|---|---|
| `FAB_EXPANDED` | 44 | 展开图标边长 |
| `FAB_TAB_VISIBLE` | 20 | 吸附后可见竖条宽度 |
| `FAB_TAB_HEIGHT` | 44 | 吸附后竖条高度，与图标边长一致 |
| 手机命中宽度 | `FAB_TAB_VISIBLE + 10` = 30 | 可见 20px，触摸区 30px，手指好点 |
| `FAB_DOCK_THRESHOLD` | 24 | 展开盒边缘到屏幕边缘的距离小于此值即吸附 |
| `FAB_DRAG_SLOP` | 5 | 位移小于此值视为点击 |
| `FAB_SAFE_PADDING` | 4 | 自由悬浮时的内边距；**吸附时左右贴 0** |

吸附时左右贴 0 是必须的，早期对吸附也套了 4px 内边距，屏幕上会空出一条。

**吸附判定**：用**展开后的完整盒子**左右边缘到屏幕边缘的距离，不取中心点。吸附态本身只有 20px 宽，用中心点会算偏。这是 Izumi 源码注释里点明的一条（`never its center`）。

**竖条绘制**：容器在吸附态是透明的，可见条用 `::after` 画在贴屏幕的一侧——`dock-left` 时 `left:0`，`dock-right` 时 `right:0`。方向搞反会出现「容器贴边但可见条离屏幕 20px」的假空隙。

**手势实现**

全程 Pointer Events 单一通道，不用 mouse/touch 两套并行（并行必然互相打架）：

- `pointerdown` 记录起点、`setPointerCapture` 防滑出元素丢事件
- 桌面端 `preventDefault`，**移动端不阻止**——阻止会破坏移动浏览器的合成事件链
- `pointermove` 位移超过 5px 才判定为拖动，一旦拖动立刻解除吸附、切完整图标、跟手移动
- `pointerup` 统一判定：没移动=轻点，移动了=拖动收尾（按阈值吸附或保留自由位置）
- `pointercancel` / `lostpointercapture` 回滚到手势开始时的位置
- 原生 `click` 一律 `stopPropagation + preventDefault`，避免与 pointerup 双重触发

**点击语义**：吸附态点击 = 只恢复成自由悬浮，**不打开面板**；自由态点击 = 打开面板。照 Izumi 的 `activate` 写法（`if (iconDock) { restoreIcon(); return; }`）。

**挂载点**：`#eo_fab`，`role="button"`、`tabIndex=0`，支持回车/空格触发。

### 5.2 面板

全屏覆盖层，不是小浮窗。

**运行日志页**（2026-10-30 新增）
内存环形缓冲，最多 500 条，刷新即清空，不落盘、不写进聊天。四个级别：

| 级别 | 函数 | 用途 |
|---|---|---|
| 信息 | `log()` | 用户关心的结果：生成成功、盘点完成、世界书写入/删除、事件收尾、模式切换、保留清理 |
| 警告 | `warn()` | 能继续但要留意的降级：适配器降级、模型没按格式返回、兜底解析、条目已不存在 |
| 错误 | `error()` | 真失败：生成/盘点失败、世界书校验不通过、回读不一致、拒绝删除他人条目 |
| 调试 | `debug()` | 排障细节：上下文规模、世界书写入明细、解析键名、模型耗时。**需在设置页打开「调试日志」才收集** |

- 标题下方一排筛选按钮：全部 / 调试 / 信息 / 警告 / 错误，每个带实时条数，选中项高亮
- 筛选状态存模块级变量，切页签不丢
- 日志按时间正序，渲染后自动滚到底（同步 + rAF + 60ms 补一次），一进来就看到最新
- 记忆来源判定做了**去重**：签名（适配器 + 是否降级 + 数据量描述）不变就不重复记。
  否则每点一次设置页就刷一条

**模型 API 多配置档**（2026-10-30 新增）

酒馆 `generateRaw` 的 `api` 参数只能选连接源类型，**不能指定 base URL 和密钥**，所以分两条路：

| 模式 | 走什么 | 可配置 |
|---|---|---|
| `main` 跟随酒馆主连接 | `generateRaw` 不带 api | 无需配置，默认档 |
| `tavern` 走酒馆连接源 | `generateRaw({ api, model, responseLength })` | 连接源类型（12 种）、模型名、输出上限 |
| `direct` 直连接口 | 扩展自己 `fetch` 到 `/chat/completions` | base URL、密钥、模型名、温度、输出上限 |

- 每档可「测试连接」：临时切到该档发一条极短请求，回报耗时与返回片段，测完切回原档
- 直连的地址填 `…/v1` 或 `…/v1/chat/completions` 都能自动补全
- 直连受**浏览器 CORS 限制**，接口必须允许跨域
- 密钥存在酒馆扩展设置里，与酒馆自身存储 API 密钥的位置相同，未额外加密
- 设置迁移保证 `main` 档一定存在，`activeProfileId` 失效时回落 `main`

分页的理由是内容量：一页铺开时手机上要滚动很久才能摸到操作按钮。

**待选草稿可编辑**（2026-11-01 新增；同日先做中文表单，后改为直接改原文）

生成出来的待选事件（`status: 'draft'`）可以直接改，不用回到输入框重生成一遍。编辑框是**一个可改的大文本框**，装的整份大纲原文，像改文档一样直接编辑（用户原话：「不能在点击编辑后，用户可以直接改展现出现的大纲文字吗，就像一份可以编辑的文档，当然保存时是需要做格式检查，确保用户的编辑不能破坏格式」）。

| 项 | 做法 |
|---|---|
| 正文 | 原文 `outlineRaw` 是唯一正文。保存时 `parseOutline()` 重新解析成结构 `event.outline`，与模型原输出走同一条路径，「看大纲」「采用写世界书」都只读结构 |
| 编辑区 | 单个 textarea（`eo-outline-editor`），Tab 键插两个空格不跳焦点（YAML 缩进敏感）；下方实时显示行数、字数、有无未保存改动 |
| 代码围栏 | 模型给的原文外面套着 ```yaml，打开时用 `stripCodeFence()` 剥掉只留正文——围栏不是大纲内容，留着碍眼也容易被误删；保存时 `wrapCodeFence()` 按打开时的状态包回去，`outlineRaw` 与模型原输出保持同一形态 |
| 键名中文 | 编辑框里显示中文键（`event_name` → `事件名`、`nodes` → `信息节点`），缩进和取值都不动；保存前 `keysToEnglish()` 换回英文键。`keysToChinese()` 返回 `{text, backMap}`，记下每行原本用的英文键，转回时对号入座，`role`/`identity` 这类共用一个中文名的键不会被改写；模型原稿本来就是中文的键（`内容:`、`风险:`）记作 `__CN__`，原样保留不翻译 || 格式检查 | 保存前先判定，分硬错/软错两级 |
| 硬错（拒绝保存） | 解析不出任何字段、内容为空、**一个信息节点都没有**。第三条是缩进被改乱时的兜底：解析器很宽容，字段还在但节点认不出来，存下去就是空壳。抛错后原文一个字都不落盘，编辑框不关，接着改 |
| 软错（只警告） | `checkOutlineRefs` 查节点编号跳号、路径 `node` 与 `refute_by` 引用不存在。这类问题照常保存 |
| 试检 | 「检查格式」按钮走 `checkEditedRaw()`，与保存同一套判定，不落盘先看结果 |
| 兜底 | 「从结构重建」用已保存的结构重新生成文本，原文丢了才用得上 |
| 名字与简介 | 以原文里的 `event_name` / `event_brief` 为准，不再单独填；改过名字清掉 `autoNamed` |
| 状态标记 | 每次保存写 `editedAt` / `editedCount`；`parseQuality` 用 `checkOutlineShape` 重算 |
| 边界 | **只能编草稿**。已采用（`active`）的大纲已写进世界书并作为盘点基准，中途改口径不可追溯；要换就废弃后重新生成 |
| 不碰世界书 | 编辑只动 chatMetadata，与 `commitDraft` 的写入路径无关，测试里有断言 |

三处实现：`saveDraftEdit()`（保存与格式校验）、`checkEditedRaw()`（只检不存）、`outlineToYaml()`（结构转 YAML，「从结构重建」用）。
界面态 `editingDraftId` / `draftEditBuf` / `draftEditIssues` 都是模块级变量，重渲染不丢；编辑缓冲只有 `text` 和 `original` 两个字段，取消时比对 `original` 判断有没有改过。

原来的中文表单（`outlineToForm` / `formToOutline`、`FORM_SPEC`、`CN_TO_EN`、`CHAR_SIDE_EN` 等）在同日删除：按字段拆表单会拆散编号与引用的上下文，改一句话、调一个编号本来就该在原文上做。


**结构规范化**（2026-11-01 补）

提示词里要求的是英文键，但模型在长输出里会漏改一两个，写成中文（实测 8 份真实卡里，
有一份 `paths` 是 `step` 英文、`内容`/`节点`/`风险` 中文混着写）。做法是在解析层统一规范化，
而不是让下游到处写 `p['内容']` 这种兼容判断：`parseOutline()` 解析完立刻过 `normalizeOutline()`，
把中文键转成英文，之后全流程只面对一套键名。

两处要按上下文判断，因为是同名不同义：

- `节点`：在 `paths` 里模型常用来写「必经/可跳过」，那是 `must`；写成数字或编号数组才是 `node`（节点编号）。
- `内容`：在 `nodes` 里是节点正文 `info`，在 `paths` 里是路径描述 `route`。

递归要覆盖所有层级。第一版只往 `paths`/`nodes` 下钻，结果 `event_type`、`characters`、`time_pressure`、
`danger` 里的中文子键全被漏掉，实测才发现。数组元素要沿用上层上下文，否则角色数组里的 `名称`/`身份` 识别不出来。

规范化做了多少、有没有同名冲突，用 `debug()` 记一行日志，不打扰用户。这是「模型没按格式来」的可观测证据。
列表渲染的两条硬规矩（2026-11-01 踩过：点编辑整页空白）：

- 渲染循环里跳过某一项只能用 `continue`。`for (const d of drafts)` 里一个裸 `return`
  会把后面所有草稿连同容器 append 一起跳过，页面只剩标题。`check-docs.js` §7.5 会扫这条。
- 每张卡的展开体（编辑框 / 大纲预览）自己包 try/catch，渲染失败只坏这一张，不能拖垮整页。


- 悬浮窗：自由态点击
- 扩展菜单 `#extensionsMenu` 项「事件大纲」，按钮可能晚于本扩展渲染，用 1.5s 间隔轮询添加，30s 后停止

**风格**：延续 scene-map 的暖色系（`#fff3d6`→`#f5d080` 渐变，边框 `rgba(184,134,11,.55)`）。

### 5.3 移动端

## 6. prompt 组装

### 6.1 偏好档位

原词每个子项的第一档是「按照委托等级或具体事件难度自行设定」。问题是：难度本身也要设，容易绕圈。

**当下实现**（2026-10-31 改版，覆盖此前版本）：

子项只有一个「自行设定」档，措辞随难度等级动态变，不再两档并存。

| 状态 | 子项里「自行设定」显示为 |
|---|---|
| 难度等级 = 根据当前情况自行设定（默认） | 根据当前情况自行设定 |
| 难度等级 = 任一的具名档位 | 根据难度等级自行设定 |

- 该项原名「委托等级」，档位是村中琐事 / 城镇委托 / 王国要务 / 禁忌事件。
  **这套词绑死了奇幻中世纪**，换成克苏鲁、校园、机甲、现代都市就都不合用，
  2026-10-31 改名为「难度等级」并换成描述难度的通用档：
  日常琐事 / 小麻烦 / 正经事件 / 重大危机 / 生死关头（另加首项「根据当前情况自行设定」）
- 档位可在**设置页「难度档位」**整组自定义：每行一个，从低到高。
  有些角色卡自带分级（F 到 SSS、「见习/正式/精英」），把卡里的说法原样填进去即可。
  留空或全空白则回落到内置默认档
- 存 `extension_settings.event_outline.preset.difficultyLevels`，空数组表示用默认
- 旧事件卡的兼容：`prefs.commissionLevel` 由 `normalizePrefs` 迁到 `difficultyLevel`，
  旧档位按量级映射（村中琐事→日常琐事、城镇委托→小麻烦、王国要务→重大危机、禁忌事件→生死关头），
  未登记的旧值原样保留；文案里的「委托等级」统一替换成「难度等级」
- 三组可折叠偏好（推理难度 / 危险程度 / 时间压力）各有「大致 / 详细」两种编辑方式：
  - **大致**：一个档位下拉，选中后一次性写满该组全部子项。档位 = 「自行设定」+ 四个粗档（轻松/常规/硬核/极端，另两组为安全/凶险/致命、宽松/紧迫/绝命）
  - **详细**：逐项下拉，可拼出粗档覆盖不了的组合
  - 切换只重绘该组内容区，折叠块本身不动（否则会自己折回去）
- 「自行设定」档在**大致和详细两种模式下措辞一致**。曾出现大致档位写死成常量的 bug，已修
- 拼 prompt 时，`根据难度等级自行设定` 会补成 `根据难度等级「{等级}」自行设定`，
  并在末尾加一句说明，要求模型按该等级成套推导、同组内互相匹配（见 6.2）

**语义边界**（2026-10-31 修）：

早期几项取值的语义重叠，同时选重时模型会理解成「要特别狠」，输出过度狠辣的事件。
四处重叠已拆开，并在 prompt 里明令不要叠加：

| 项 | 只负责回答 | 不再负责 |
|---|---|---|
| 致死性 | 丢命的可能性大小 | 后果轻重（那是失败后果） |
| 失败后果 | 失误一次的代价 | 是否致死 |
| 容错率 | 允许错几次 | 后果轻重（低容错≠后果更重） |
| 超时后果 | 时间耗尽时的结局 | 角色死亡（那种分量由致死性+失败后果表达） |
| 倒计时 | 玩家知不知道有期限 | 紧迫感 |
| 时长 | 节奏紧迫感 | 有没有期限 |

取值也随之调整：失败后果「不可逆的惨重损失」→「无法挽回的损失」；
超时后果「角色死亡或不可逆损失」→「局势不可逆转」；容错率改为带次数说明
（高（可多次试错）/ 中（两次）/ 低（一次即定局)）；倒计时改为
「没有硬期限 / 有期限但不知道 / 有期限且明确知道」。
旧事件卡的取值由 `normalizePrefs` 按下标逐字段迁移，不做全局替换
（「高/中/低」在致死性里同样合法）。

**形态类选项**（2026-10-31 新增）：

前四项覆盖难度与危险，但控制不了事件本身的形态尺寸。新增四个独立项，
不并入三组（否则粗档要一并定义，会把选择权收回去）：

| 项 | 取值 | 对大纲的约束 |
|---|---|---|
| 节点数量 | 少（4-6）/ 中（7-9）/ 多（10-14） | nodes 数组长度落在该区间 |
| 参与者规模 | 少数（1-2 人）/ 适中（3-5 人）/ 庞大（6 人以上或牵扯势力） | characters 的角色数量与之相称 |
| 节奏结构 | 单点突破 / 多层递进 / 并行多线 | paths 的组织方式体现该结构 |
| 与前事关联 | 完全独立 / 承接已有线索 / 主动留下后续伏笔 | 决定是否引用【当前剧情】里的既有伏笔 |

这四项填了就在 prompt 生成「事件形态」小节，作为硬约束；填「自行设定」则不出现该小节。
节点数量会直接影响盘点负担——节点越多，打勾越费事，所以值得让用户提前定。

### 6.2 事件类型与事件名

**事件类型**（生成页、事件名与体验偏好之间）：

| 项 | 形式 | 约束 |
|---|---|---|
| 主类型 | 单选下拉 | 8 项：案件推理/谈判交涉/探险探索/生存危机/社交博弈/战斗冲突/日常委托/禁忌秘辛；首项「根据当前情况自行设定」 |

两者都可留空。空时 prompt 写「未指定，请根据当前剧情判断/自行搭配」，**不留空给模型猜**：

**事件名自动生成**：事件名输入框可留空。留空时 prompt 去掉 `为即将开始的【X】`，
改为要求模型读当前剧情自己起一个 4-12 字中文名写进 `event_name`，
并写一句 `event_brief` 说明这事件要解决什么。

取名优先级：**用户填的 > 模型 event_name > 日期兜底**（`未命名事件（日期）`）。
后两种都写日志（模型命名记 info，日期兜底记 warn 作为格式异常信号）。
事件卡存 `autoNamed` 标记与 `brief` 字段。

## 7. 解析

### 7.1 大纲（宽松解析）

模型返回可能是：纯 YAML、```yaml 包裹、带客套话。

策略：
1. 提取 ```yaml ... ``` 代码块
2. 提取不到代码块则整段当 YAML 解析（`fromFallback = true`）
3. 按行解析缩进层级（递归下降，支持映射、列表、对象列表、标量列表）
4. 解析结果为空 → 保留 `outlineRaw`，面板显示原文

不引入 YAML 库（无构建限制）。

**实现要点（踩过的坑）**：

去注释必须识别引号：只有引号外、且前一个字符是空白的 `#` 才算注释。早期实现无条件按 `#` 切，导致 `core_truth: 含#号的真相` 被切成 `含`。

空值键的容器类型要事后判定。`nodes:` 后面跟 `- id: 1` 是列表，跟 `type: x` 是映射，写解析器时不能提前建 `{}`，否则遇到 `- ` 时转不成数组，整段 `nodes` 丢失——节点清单是本扩展的核心，丢了等于功能失效。正确做法是先窥探下一个有效行的缩进与形态再决定容器类型。

行内数组 `[1, 2, 3]` 要支持，大纲里 `min_nodes_for_deduction` 常这么写。

**块标量 `key: |` 必须支持**。模型写多行中文正文（`core_truth` 尤甚）时几乎一定用 `|`。早期版本只把 `|` 当普通字符串值，于是 `core_truth` 解析成字面量「|」，后面所有缩进行被当成不属于任何键的行跳过，**`nodes` / `characters` / `paths` / `forbidden` 整块丢失**——实机表现是三个事件卡全都只剩 `event_name` / `event_brief` / `event_type` / `core_truth` 四个键，节点进度永远 0/0，界面只能退回去显示原始 YAML，用户看到满屏英文键名。

正确做法：预扫描阶段先标出哪些行属于块标量正文（缩进大于键所在行的行），`readBlockScalar` 原样取出、去掉公共缩进，`|` 保留换行、`>` 折成空格。

旧事件卡不必重做：`outlineRaw` 一直完整保存着原文，`healOutline` 在读取事件时发现 `nodes` 为空就用新解析器重建一次。实测「入校三印」重建出 8 个节点、4 类角色。

**界面不展示英文字段名**。`renderOutlineText(outline)` 把结构渲染成中文分段文本（一句话简介／事件类型／核心真相／信息节点／推理必需节点／参与角色／推进路径／禁止事项），键名与节点类型走 `OUTLINE_KEY_LABEL`、`NODE_TYPE_LABEL`、`EVENT_TYPE_LABEL` 三张对照表，认不出的键保留原样。原始 YAML 收进折叠区，标注「模型原始输出（排查用，含英文字段名）」。

**测试**：`scripts/test-parser.js`，36 项，覆盖块提取、标量类型、对象列表、标量列表、注释剥离、无 fence 降级、盘点 JSON 与尾逗号容错、大纲完整性检查。`scripts/test-event-outline.js` 里另有块标量与中文渲染的回归用例。

### 7.3 日志与失败可见性

这一节是补的教训。块标量 bug 在实机上跑了很久没被发现，原因不是日志级别不够，而是**失败没人看得见**：解析器把 `nodes` 整块吞掉后只落了一句 `warn`，事件卡照常创建、世界书照常写入，界面上看起来跟正常生成一模一样。用户以为是设计如此。

现在分四层保证失败能被看到。

日志四级：`debug`（默认不收集，设置里开开关才收，记录键名、字数、条目清单这类细节）、`info`（每次生成的关键节点与统计）、`warn`（结构缺失、降级、截断）、`error`（解析彻底失败、世界书读不到、上下文为空）。

`checkOutlineQuality(parsed)` 在大纲解析后逐项核对：节点缺失或不是列表、节点是空列表、节点没编号、节点没内容、推理必需节点缺失、角色缺失或为空、简介与核心真相缺失。返回 `{ok, missing[], summary}`，结果存进事件卡的 `parseQuality` 字段留档。

三个界面出口，缺一不可：

- 进度条里插一行「⚠ 结构不完整：…」，生成当场就能看见
- 事件详情页顶部红色警示框，只要 `parseQuality.ok === false` 就一直挂着，提示可以重新生成
- 日志页标签挂红色未读角标，`warn` 与 `error` 都计数，点进日志页才清零

另外补了上下文汇总日志：一行列出世界书、事件卡、纪要、楼层各多少字，合计多少字；总量低于 500 字时报警，因为那意味着模型基本在凭空发挥。

**教训**：静默降级等于没测出来。解析器可以容错，但容错之后必须留下痕迹，且痕迹要出现在用户当下看着的界面上，不能只躺在日志里。

### 7.4 节点字段名的容错

**根子在 prompt，不在渲染**（2026-10-31 定）。先前一直靠渲染层追着模型的键名跑：
模型换一套中文键，就补一批容错，下次它再换，又得补。这是治不完的。

现在 prompt 里直接给出完整的 YAML 骨架，51 行，每个键的确切拼写都列出来，
并写明「键名一律用英文小写加下划线，不许改写成中文、不许自造同义词、不许增减层级，
只有尖括号里的内容要你填」。原来只规定了节点字段和顶层键，角色内部字段
（`name` / `identity` / `motive` / `cost` / `reason` / `resolvable_by` / `info_known`）
和路径内部字段（`route` / `must` / `risk` / `fail`）从没写死过——模型就是在这里自由发挥的。

配套加了两样：

- **漂移检查**：`checkOutlineQuality` 结果多返回一个 `drift` 数组，
  检查角色名是否用 `name`、节点内容是否用 `info`、路径是否用 `route` 和 `must`。
  不判失败（渲染有容错，还能看），只在日志里 `warn` 一句，方便判断 prompt 要不要再收紧
- **渲染补全**：`time_pressure` 和 `danger` 以前是模型写了但界面不显示，现在会输出；
  事件类型的 `主类型 / 次类型`、角色的 `identity` 也补进了取值名单

容错名单仍然保留——模型不听话时至少还能看。但正常路径应该是它照着骨架写。

模型给节点正文起的键名不稳定：同一张卡上，「入校三印」用 `info`，「入学首日」用 `points_to`。prompt 原先只说「指向的信息或后果」，没定键名，模型就自己造。

两头一起收紧：

- prompt 里写明节点字段固定用 `id` / `type` / `trigger` / `info` / `refute_by`
- 代码侧不信任单一键名，`nodeText()` 依次尝试 `info / desc / content / points_to / point_to / pointsTo / detail / description / what / reveal`，`nodeTrigger()` 同理，`nodeId()` 兼容 `id` 与 `index`

这个错踩过一次：完整性检查最初只认 `info/desc/content`，于是用 `points_to` 的那次生成被判成「8 个节点没有内容」，事件详情页挂着红色警示。判定的目的报假警报正好相反——报错本身也会误伤，容错名单要覆盖模型实际会用的写法。

`healOutline` 每次读取事件时按当前规则重判一遍 `parseQuality`，所以判定规则变严或放宽后，旧事件的结论会跟着更新，不会一直挂着过期的红框。

**推进路径同理**（2026-10-31 修）。模型实际给的是
`{step, node, route, must, risk, fail}`，而渲染只认 `desc/detail` 与 `failure`，
于是一整段路径只剩「风险」两行看得见——路线、是否必经、失败后果全丢了。

现在的取键规则：

| 想要什么 | 依次尝试 |
|---|---|
| 标题 | `step`（非数字时）、`name`；都没有就用 `route` 首句 |
| 路线 | `route` / `desc` / `detail` / `description` |
| 存在理由 | `why` / `reason`（大纲外分支专用） |
| 是否必经 | `must` / `required` / `required_nodes` |
| 失败后果 | `fail` / `failure` / `consequence` |

`step` 是数字时只当序号，不能再当标题，否则会渲染成「1.（节点 1，必经）」。

**中文字段名也要认**（2026-10-31 修）。同一次生成里，模型整套换成了中文键：
角色是 `名称 / 身份 / 动机 / 条件或代价`，路径是 `内容 / 节点 / 风险`。
当时角色全渲染成「未命名」、路径 11 步全空，只剩风险可见。

| 位置 | 依次尝试 |
|---|---|
| 角色名 | `name` / `名称` / `角色名` / `姓名` |
| 角色身份 | `role` / `身份` / `职衔` |
| 角色动机 | `motive` / `动机` |
| 代价 | `cost` / `条件或代价` / `代价` |
| 掌握信息 | `info` / `info_known` / `掌握信息` / `掌握` |
| 路线 | 追加 `内容` / `路线` |
| 存在理由 | 追加 `存在理由` |
| 失败后果 | 追加 `失败后果` |

还有个坑：模型会把「必经」写进 `节点` 字段。直接当节点号拼接会渲染成
「节点 必经」，所以先判断是不是纯数字——是数字才当节点号，否则当必经标记。

### 7.5 界面的 busy 状态

`busy` 是模块级变量，但面板每次 `renderPanel()` 都会重建 DOM。早期版本只在点击时禁用按钮，于是切换标签页再切回来，按钮是全新的、可点的，用户能对同一次生成点第二次。

现在两个操作按钮（开始生成大纲、开始盘点）在创建时就按 `busy` 决定禁用状态与文案（「正在生成…」/「正在盘点…」），点击回调里也先 `if (busy) return` 兜一层。

进度条挂载位置：面板中部有一个 `#eo_progress_host` 锚点，紧跟在操作按钮和结果提示下方，`renderProgress()` 优先往锚点里塞，找不到锚点才退回面板顶部。这样进度出现在用户眼睛正在看的地方，而不是面板最上面。

### 7.2 盘点（结构化）

风险：opencode.ai 接入点是否支持 JSON Schema 未知，**需实测**。不支持则退回宽松解析 + 正则提取字段。
