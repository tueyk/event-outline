## 1. 使用口径

**用法说明（前置条件、完整流程、打勾模式怎么选、记忆来源与模型 API 怎么配、
日志页怎么看、出问题先看哪）全部在仓库根目录 `README.md`，本节不再重复。**

这里只留工程侧的口径：设置项的技术参数、以及界面上看不出来的实现行为。

### 1.1 设置项的技术参数

| 设置 | 选项 | 默认 | 生效 | 存储 |
|---|---|---|---|---|
| 模型 API | 多配置档，每档三选一：跟随酒馆 / 走酒馆连接源 / 直连接口 | 跟随酒馆 | 下次生成 | `apiProfiles[]` + `activeProfileId` |
| 记忆来源 | 自动 / shujuku 纪要 / 仅最近楼层 | 自动 | 下次盘点 | `memory.source` |
| 最近楼层 | 1–100 | 15 | 下次盘点 | `memory.recentFloors` |
| 打勾模式 | 自动 / 半自动 / 手动 | 自动 | 下次盘点 | `tracker.mode` |
| 自动检测间隔 | 每 N 层（玩家楼 + AI 楼）触发，0 = 关 | 10 | 立即 | `tracker.autoEveryFloors` |
| 历史保留 | 完结 / 废弃上限 | 20 / 3 | 下次收尾 | `retention` |
| 悬浮窗 | 开 / 关 | 开 | 立即 | `ui.floatingEnabled` |
| 调试日志 | 开 / 关 | 关 | 立即（只影响 debug 级是否收集） | `debug` |

设置存 `extension_settings.event_outline`；事件卡存 `chat_metadata.event_outline`。
`apiProfiles` 迁移时保证 `main` 档一定存在，`activeProfileId` 失效时回落 `main`。

### 1.2 记忆来源的当前判定

- 自动模式按优先级探测，都没有就退仅最近楼层；手动指定的探测失败会**自动降级并黄字提示**
- 纪要表按 `name === '纪要表'` 识别，找不到再退回 key —— 换模板不会静默失效
- 填表模式读 `chat_metadata.TavernDB_ACU_ScopedConfig`，只在内部用，不进设置
- **当前召回**：LLM 模式只放前 60 条概览，没有第二次点名精读；其余模式取最近 30 条正文
- 判定结果做了**去重**：签名（适配器 + 是否降级 + 数据量描述）不变就不重复记日志，
  否则每点一次设置页就刷一条

### 1.3 打勾三档的内部状态

| 模式 | 模型判定后 |
|---|---|
| 自动（默认） | 直接写入，跳过 `nodeVetoed`，同时更新误导与大纲外路径 |
| 半自动 | 记进 `pendingNodes` 存起来，盘点页「待确认的建议」列出，点确认才写入 |
| 手动 | 不写入，只留报告 |

三种模式下手动点节点总是有效。撤掉已勾节点会记进 `nodeVetoed`，自动模式不再重复勾。
节点标记前缀：已触发 `✓`，待确认 `◐`。

## 3. 工程约束

### 3.1 硬约束（发布前必须成立）

- 单文件 IIFE，无 `import`、无构建、无第三方库
- 只用 `window.SillyTavern.getContext()`，加载时不同步读聊天
- 不写聊天楼层、不写变量、不改角色卡
- 世界书只动 `▸事件｜` 前缀条目，删除只按记录的 uid 删
- 凭证不进界面、日志、console、代码

### 3.2 发布自查清单

- [ ] manifest 有 `js` / `css` / `display_name` / `loading_order`，`loading_order` 是纯数字
- [ ] `index.js` 没有 `import`
- [ ] 不依赖 `requires` 里没列的扩展
- [ ] 入口按钮带文字、放左上角、`z-index: 999999`
- [ ] 出错时 console 有可读日志，界面不白屏
- [ ] 事件监听有 `CHAT_CHANGED`（是否加 `MESSAGE_RECEIVED` 见 §2 第 2 条）
- [ ] 世界书只动 `▸事件｜` 前缀，其余条目零变化

### 3.3 日志

四个级别，全部带 `[事件大纲]` 前缀，同时进内存环形缓冲（最多 500 条），面板「日志」页可见，
不落盘。只记动作，不记聊天正文。

| 级别 | 函数 | 什么时候用 |
|---|---|---|
| 信息 | `log()` | 用户关心的结果：生成成功、盘点完成、世界书写入/删除、事件收尾、模式切换、保留清理 |
| 警告 | `warn()` | 能继续但要留意的降级：适配器降级、模型没按格式返回、兜底解析、条目已不存在 |
| 错误 | `error()` | 真失败：生成/盘点失败、世界书校验不通过、回读不一致、拒绝删除他人条目 |
| 调试 | `debug()` | 排障细节：上下文规模、世界书写入明细、解析键名、模型耗时、校验通过。**只有设置页打开「调试日志」才收集** |

新加日志时的判断口诀：**用户需要知道结果的用 log，数据有问题但没崩的用 warn，
崩了或数据可能写错的用 error，只有排障时才有人看的用 debug**。
世界书写入这种高风险路径必须同时有 log（成功）和 error（失败）两条。

日志页支持按级别筛选，并显示各级别条数。

## 4. 版本与提交（提交必须经用户授权）

### 4.1 版本规则

- 唯一真源是 `src/event-outline/manifest.json` 的 `version`，`index.js` 的 `const VERSION`
  必须同步（`check-docs.js` 会校验）
- 语义化：修 bug 升 patch，加功能升 minor，改数据结构升 major
- tag 格式 `v<版本>`，如 `v0.1.0`，与 manifest 完全一致
- **版本号只在申请 git 提交时问用户**（2026-10-30 危晓定）：平时改代码、部署、调试
  都不提版本的事，也不擅自改 manifest 的 `version`；到提交那一步再在 §4.3 第 5 项里
  给出「现在多少 → 建议升到多少 → 哪一档」，由用户定

### 4.2 提交授权（2026-10-30 危晓定，硬性）

- **任何 git 提交都必须先经危晓明确授权**；`add` 之后不得自行 `commit`
- 未获授权时只做本地改动与自检，不碰仓库历史
- tag、push 同属对外可见动作，一并需要授权（`push` 经 §5.2 的中继链路，对 GitHub 可见）
- 授权只对当次生效，不延续到下一次改动；改完新的内容要重新申请

### 4.3 申请授权时必须给出的信息

缺任何一项都算信息不完整，授权前先补齐，不要用「已改好，可否提交」一句话打发：

| # | 项 | 要求 |
|---|---|---|
| 1 | 拟提交范围 | 逐条列出将要 `add` 的文件，标明新增 / 修改 / 删除 / 改名，不写「若干文档」 |
| 2 | 改动内容 | 每个文件改了什么、为什么改，用一两句说清结论，不贴大段 diff |
| 3 | 行为影响 | 哪些用户可见行为会变、哪些不变；有破坏性变更要单独点出 |
| 4 | 待提交清单外的残留 | 明确说明还有哪些改动**不进**这次提交，以及原因 |
| 5 | 版本号 | 现在是多少、建议升到多少、按语义化属于哪一档（patch / minor / major） |
| 6 | 拟定的提交信息 | 完整的 commit message 全文，含正文要点 |
| 7 | 配套动作 | 是否打 tag、tag 名、是否 push、推到哪个远端；不做也要写明「不推」 |
| 8 | 自检结果 | 三个脚本（`test-event-outline` / `test-parser` / `check-docs`）的实际结果，不能只说「通过」 |
| 9 | 风险与回滚 | 出问题怎么撤（`git revert` / 重新部署 / 删扩展目录），有无不可逆的数据副作用 |
| 10 | 授权粒度 | 请用户选择：只提交 / 提交加打 tag / 提交加打 tag 并推送，三档让他挑 |

## 5. 部署与运维

### 5.1 部署与回滚

```bash
bash scripts/deploy.sh event-outline             # 打包上 VPS + 回读 sha256
bash scripts/deploy.sh event-outline --dry-run   # 只看会传什么
```

- 前端扩展不需要重启容器，`Ctrl+Shift+R` 硬刷生效；manifest 能被公网取到（HTTP 200）即已识别
- 代码回滚：`git revert` + 重新部署；或删 `/opt/tavern/extensions/event-outline` 后刷新
- 数据回滚：删 `chat_metadata.event_outline`；世界书里按 `▸事件｜` 前缀手删

**部署不需要请示**（2026-10-30 危晓定）：点「危晓改好的代码，自测后可直接挪到 VPS 让用户看功能」。

- 前提：本地自测已通过（§5.3 第 3、4 步），`node --check` 与三个脚本全过
- 直接执行 `bash scripts/deploy.sh event-outline`，回读 sha256 后把结果报给用户
- 部署是整目录覆盖 `/opt/tavern/extensions/event-outline`，不影响正在进行的对话——
  事件状态存在对话的 `chat_metadata` 里，不在扩展目录；用户硬刷页面即可看到新功能
- 部署**不改变版本号**，版本号只在 §4.1 说的提交环节讨论
- 只有违背上述前提（自测没过）或涉及扩展目录以外的改动时，才需要先报到

### 5.2 远程仓库与沙箱限制

- 通道：本地 → VPS 裸库 `ssh://tavern/home/ubuntu/git/event-outline.git` →
  `post-receive` 钩子走 SSH 443 转推 `github.com:tueyk/event-outline.git`；
  日志 `/home/ubuntu/git/event-outline-push.log`，见 `exit=0` 才算到 GitHub
- 原生命令不可用（沙箱禁止 git fork 传输层），一律用脚本：

```bash
bash scripts/remote-sync.sh ls-remote | push | fetch | pull | push-log
```

- 沙箱内**能**跑：`rev-parse` / `log` / `status` / `cat-file` / `rev-list` / `archive` /
  `pack-objects --stdout` / `index-pack` / `update-ref`
- 沙箱内**不能**跑：`push` / `fetch` / `ls-remote` 走网络、`git bundle`
- **凡是会写 `.git/index.lock` 的操作都被拒**：实测 `git add` / `git mv` / `git rm` /
  `git commit` 全部报 `Unable to create '…/.git/index.lock': Permission denied`，
  根因是仓库目录 ACL 带 `Everyone:(I)(CI)(DENY)(DC)`，而沙箱子进程拿不到写索引的权限
- 沙箱内**能做**的提交路径：只做本地文件改动与自检，`add` / `commit` 由危晓在编辑器里执行
  （见 §4.2、§5.3 第 6 步）
- 删文件、改名同样优先在资源管理器里做，不要反复重试同一条失败命令；
  失败一次就该判定为沙箱限制，而不是命令写错

#### 沙箱写文件：bash/node 写不了，edit 工具能写（2026-10-30 实测）

同一时刻、同一文件，两条写入路径权限不同，别混着判断：

- **bash 里的写文件一律被拒**：`echo >`、`cp`、`python open('w')`、`node fs.writeFileSync`
  全部报 `Permission denied` / `EPERM`，连工作区根目录也写不进
- **DSH 的 edit / write 工具能正常写入**：同一文件同一时刻改得动
- 所以「bash 写不进去」**不等于**「工作区被锁」，也不等于 VSCode 占用了文件；
  先换 edit 工具试一次再下结论，别急着让用户关编辑器
- 例外：`git add` / `git mv` / `git rm` 连 edit 工具也绕不过（要写 `.git/index.lock`），
  那部分只能由用户在编辑器里执行（见 §4.2）

### 5.3 改动流程

1. 定验收标准：改了什么行为、怎么算成功
2. 只改 `src/event-outline/`
3. 自查：`node --check index.js`，manifest 用 `JSON.parse` 验一遍
4. 跑测试：`node scripts/test-event-outline.js`、`node scripts/test-parser.js`、
   `node scripts/check-docs.js`
5. 部署并回读 sha256，把结果报给用户（**不用请示**，见 §5.1）
6. 想进仓库时再走提交：按 §4.3 申请授权，同时给出建议版本号（**版本只在这里谈**）
7. 授权后由用户在编辑器里 `add` / `commit` / 打 tag / 推送；沙箱写不了索引（§5.2，
   `git add` 会被拒），所以提交这一步不归 agent
