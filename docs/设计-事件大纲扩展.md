## 1. 技术底座

VPS 上酒馆是 **SillyTavern 1.19.0**，容器 `sillytavern`，镜像 `ghcr.io/sillytavern/sillytavern:1.19.0`。

`/opt/tavern/extensions` 挂到容器内 `public/scripts/extensions/third-party`。

已装扩展（6 个）：JS-Slash-Runner 4.11.3、ST-BaiBai-Book、ST-Prompt-Template、SillyTavern-Pathweaver、scene-map（已禁用）、shujuku 1.3。

前端扩展只需 `manifest.json` + `index.js`，不重启容器，硬刷生效，删目录即回滚。

### 1.1 可用 API（来自 `public/scripts/st-context.js` 的 `getContext()`）

| 用途 | API |
|---|---|
| 读聊天 | `ctx.chat`、`ctx.chatId` |
| 读/存 chat metadata | `ctx.chatMetadata`、`ctx.saveMetadata()`、`ctx.saveMetadataDebounced()` |
| 触发生成 | `ctx.generateRaw({prompt, systemPrompt, jsonSchema, responseLength})`、`ctx.generateQuietPrompt(...)` |
| Token 计数 | `ctx.getTokenCountAsync(text)` |
| 上下文上限 | `ctx.getMaxPromptTokens()` |
| 请求头（含 CSRF） | `ctx.getRequestHeaders()` |
| 世界书读写 | `fetch('/api/worldinfo/get'/'edit')` + `getRequestHeaders()` |
| 事件 | `ctx.eventSource.on(ctx.eventTypes.CHAT_CHANGED / MESSAGE_RECEIVED, fn)` |
| 设置持久化 | `ctx.saveSettingsDebounced()`、`ctx.extensionSettings` |

### 1.2 三个不可用的方向（已实测排除）

| 方向 | 为什么不行 |
|---|---|
| `is_system` 隐藏楼层 | `script.js:4496` `coreChat = chat.filter(x => !x.is_system)`，**模型看不到**，方向相反 |
| 靠世界书自动注入 | `generateRawData` 不调用 `getWorldInfoPrompt`，蓝灯对静默生成无效 |
| `setExtensionPrompt` 注入 | 只影响正常生成链路，对 `generateRaw` 无效 |

结论：**必须自己拼上下文**。参照实现见 §3.2。

## 3. 核心流程

### 3.1 生成大纲

```
用户点「开新事件」
  → 填事件名 + 选偏好 + 额外要求
  → buildOutlinePrompt(prefs)          // OOC 改良词 + 偏好替换
  → gatherContext()                    // 事件卡无，只需最近楼层
  → generateRaw({ prompt, systemPrompt })
  → parseOutline(raw)                  // 宽松解析
  → 存事件卡（status=active）
  → writeWorldEntry()                  // 蓝灯条目
  → 面板展示
```

### 3.2 上下文拼装（关键）

只有一条路：自己拼。参照酒馆自带 memory 扩展（`public/scripts/extensions/memory/index.js`）的做法。

它的核心逻辑（第 761 行 `getRawSummaryPrompt`）：

```js
const PROMPT_SIZE = await getMaxPromptTokens();
for (let index ...) {
    const entry = `${message.name}:\n${message.mes}`;
    chatBuffer.push(entry);
    const tokens = await countSourceTokens(getMemoryString(true), PADDING);
    if (tokens > PROMPT_SIZE) { chatBuffer.pop(); break; }
}
```

我们的实现分三层：

```
第一层（必带）：事件卡状态
  - 当前大纲摘要
  - tracker：已触发节点、未触发节点、已推翻误导

第二层（本期）：shujuku 纪要召回
  - 取 sheet_ji_yao_biao 的「概览」列全部列出（30字×204≈6000字）
  - 让模型点名精读哪几条
  - 取被点名条目的「纪要」正文（240-480字×N）

第三层（补充）：最近楼层原文
  - 最近 15 楼（可配），跳过 is_system 和空 mes
  - 补上纪要表尚未覆盖的最新剧情

拼装顺序：
  system: 盘点/大纲指令 + 事件卡状态
  user:   纪要概览清单 → 选中纪要正文 → 最近楼层 → 实际问题
```

### 3.3 盘点

```
用户点「盘点」
  → 需要 status=active 的事件卡
  → gatherContext()（三层全用）
  → buildInventoryPrompt()
  → generateRaw({ prompt, systemPrompt })
  → parseInventory(raw)
  → 结果存 inventories[]
  → 按 tracker 模式处理打勾
  → writeWorldEntry()（覆盖更新同一条）
  → 面板展示
```

### 3.4 tracker 三档
| 模式 | 行为 |
|---|---|
| `auto`（默认） | 模型判定 → 直接写 tracker → 记 `autoCommitted` → 更新世界书 |
| `semi` | 模型判定 → 面板高亮待确认 → 确认后写入 |
| `manual` | 模型只出报告 → 全部手动勾 |

约束：
- 三档都只把**已确认部分**写进世界书
- `nodeVetoed` 里的节点，auto 模式不再自动勾
- 每次自动勾选留痕（`autoCommitted`）

### 3.5 收尾

```
点「收尾」→ 选 完结 / 废弃
  → 删世界书 `▸事件｜` 条目（按 entryUid 精确定位）
  → status 改 completed / abandoned，写 closedAt
  → 按 retention 清理超限历史卡
```

### 3.6 世界书读写（高风险，必须严谨）

接口：`POST /api/worldinfo/get`（读）、`POST /api/worldinfo/edit`（写）。

**服务端实现**（`src/endpoints/worldinfo.js:134`）：

```js
if (!('entries' in request.body.data)) throw ...
writeFileAtomicSync(pathToFile, JSON.stringify(request.body.data, null, 4));
```

要点：
- **没有增量接口**，必须整本读-改-写
- 原子写入，不会写一半崩掉

**实测安全性**（伊瑟利亚3.7：571 条 / 2.7MB / 127 个 EJS 条目）：
- 原始 2,737,968 字节，`JSON.stringify(data, null, 4)` 后**字节完全相同**
- EJS 条目数不变
- uid 0–570 连续无断档

**必做防护**：

| 措施 | 实现 |
|---|---|
| 全局写锁 | 模块级 Promise 队列，同一时刻只一个写操作 |
| 只增不改 | 只追加 `▸事件｜` 前缀新条目 |
| 写前快照 | 整本 JSON 存 `chatMetadata.event_outline.snapshots` |
| 写后校验 | 回读比对：条目数只增不减、已有条目内容未变 |
| 失败中止 | 校验不一致立即中止并提示，不重试 |
| 删除只删自己 | 只删 `▸事件｜` 前缀且 uid 匹配 |

**关于 ignoreBudget**：不需要。预算公式是 `budget = Math.round(world_info_budget × maxContext / 100)`，`world_info_budget` 默认 25，`maxContext` 取 `getMaxPromptTokens()`，走 `openai_max_context = 2,000,000`，所以预算约 49.25 万 token。

现有 48 条蓝灯（17.3 万字符）仅占约 10.8 万 token，余量 38.4 万。加 ignoreBudget 反而让条目脱离预算管理，以后调小预算时它不跟着缩。

补充：`max_context`（旧字段）是 8192 但**不生效**，不要拿它算预算。

## 4. 记忆模块适配

### 4.1 接口

```js
/**
 * @typedef {Object} MemoryAdapter
 * @property {string} id
 * @property {string} label
 * @property {() => boolean} detect          当前对话是否有可用数据
 * @property {() => Array<{code, span, summary}>} list   概览清单
 * @property {(codes: string[]) => Array<{code, text}>} read  精读
 * @property {number} maxEntries             最多返回条数
 */
```

### 4.2 shujuku 适配器（本期实现）

#### 模式背景

shujuku 有四种填表模式（源码 `Dw` 常量）：

| 值 | 名称 | 特点 |
|---|---|---|
| `classic` | 经典表格模式 | 大总结归纳，新装默认 |
| `vector` | 向量表格模式 | embedding + rerank 召回顾 |
| **`llm`** | **LLM模型逻辑召回模式** | **LLM 读纪要概览与目录，按信息缺口精读。兰开斯特卷在用** |
| `crossfire` | 交火模式 | 关键词+向量+BM25+rerank+LLM |

`llm` 模式的官方说明：「由 LLM 先读纪要概览与目录，再按信息缺口精读具体纪要区间」，优点「无可比拟的精准」，代价「每次正文生成前额外调用一次 LLM 进行记忆分析」。

**我们的召回思路和它一致**：先给概览清单，让模型点名精读。区别只是我们主动调，不塞进正文生成流程。

#### 实际数据结构（从兰开斯特堡 17.8MB 存档实测）

```
消息楼层
└── TavernDB_ACU_IsolatedData
    └── ""                        ← 隔离键（空串 = 未启用隔离码）
        ├── storageFrame          ← version: 2
        │   ├── logEntries[]      ← 增量操作日志，不是快照
        │   └── headRevision
        └── _acu_storage_version

logEntries[i] 结构：
  { seq, entryId, createdAt, source, targetMessageIndex, aiFloor,
    filledSheetKeys[], changedSheetKeys[], groupKeys[],
    operations[], baseRevision, parentRevision, commitRevision, writeSet }

operations[i].kind: "sheet_replace" | "row_upsert"
operations[i].sheet.content: [][]    ← 二维数组，第一行是表头
```

#### 表格清单（兰开斯特卷实测 8 张）

| sheet key | 名称 | 操作次数 |
|---|---|---|
| `sheet_ji_yao_biao` | 纪要表 | 33 |
| `sheet_zhong_yao_jue_se_biao` | 重要角色表 | 30 |
| `sheet_xuan_xiang_biao` | 选项表 | 29 |
| `sheet_ren_wu_yu_shi_jian_biao` | 任务与事件表 | 19 |
| `sheet_bei_bao_wu_pin_biao` | 被宝物品牌（名称待核对） | 14 |
| `sheet_quan_ju_shu_ju_biao` | 全局数据表 | 5 |
| `sheet_zhu_jue_xin_xi_biao` | 主角信息表 | 5 |
| `sheet_zhu_jue_ji_neng_biao` | 主角技能表 | 1 |

#### 纪要表结构（本期核心）

205 行 = 表头 + 204 条纪要。

表头：`["row_id","编码索引","时间跨度","概览","纪要","重要对话"]`

样例：
```
AM0204 | 1497-01-26 07:05 ~ 07:25
概览：野法师格雷夫上门点名，二人移步客栈背后谈话
纪要：危晓在公会分站板前犹豫五张委托时，门被推开，一个四十上下的野法师进来。
      此人自称韦斯林·格雷夫，从王国西北边走了十几天到此……
```

规格：概览 ≤30 字，纪要 240–480 字，编码从 AM0001 递增。

#### 读取策略

| 顺序 | 方式 | 说明 |
|---|---|---|
| 1 | `globalThis.currentJsonTableData_ACU` | shujuku 主动暴露，最简单 |
| 2 | 回放 `ctx.chat` 里的 `logEntries` | 全局变量拿不到时兜底 |

回放规则：按 `seq` 排序，依次应用 `sheet_replace`（整体替换该表）和 `row_upsert`（按 row_id 更新）。只需最终态，不需中间态。

#### 兼容性

- shujuku 不在 → 降级为纯楼层，不报错
- 数据里没有 `sheet_ji_yao_biao` → 同上
- 隔离键非空 → 用当前对话对应的隔离键（`getCurrentIsolationKey` 的等价实现：读 shujuku 暴露的设置，或默认空串）

## 6. prompt 组装

### 6.1 偏好档位

原词每个子项的第一档是「按照委托等级或具体事件难度自行设定」。问题是：难度本身也要设，容易绕圈。

**新增一档**「根据当前情况自行设定」，与原有各档并列，且**设为默认**：

| 档位 | 含义 |
|---|---|
| **根据当前情况自行设定**（新增，默认） | 模型读当前剧情与上下文，自行判断该子项取什么强度 |
| 按照委托等级或具体事件难度自行设定 | 原档：先看难度等级再定档 |
| 各具体档位 | 原词里的「充足 / 够用 / 稀缺」等 |

实现：
- 6 组 25 个子项，每个下拉第一项都是新档，默认选中
- 拼 prompt 时，新档替换成 `根据当前剧情情况自行设定`，其余各档照原文替换
- **不改动原词已列出的任何一档的措辞**

### 6.2 大纲 prompt 骨架

```
OOC: 暂停扮演。为即将开始的【{事件名}】生成完整结构大纲，用 YAML 输出，包含：
1. 事件类型与核心真相：……
2. 信息节点清单：按发现顺序列 5-8 条……
   （评审意见 2：额外输出「推进所需最少信息节点编号」）
3. 参与角色：助力者（动机各不相同，条件按实际判断）/ 阻碍者 / 知情者 / 幕后方（reveal: forbidden）
4. 推进路径：……（评审意见 3：允许新开路径，但须标注【大纲外】并说明原因）
5. 禁止事项：……
【体验偏好（已选档位）】
- 线索充足度：{值}
- 误导强度：{值}
- ……
【硬性要求（不得违反）】
- 公平性：所有指向核心真相的信息必须在事件中可获得
- 误导：允许 1-2 个，每个必须有可推翻它的反向证据（评审意见 5：refute_by 节点编号）
```

### 6.3 盘点 prompt 骨架

```
OOC: 暂停扮演，做一次状态盘点。基于本事件开场大纲和到目前为止的对话，输出：
A. 已确认信息（只列对话中已实际出现的，注明楼层）
B. 尚未触发的信息节点（对照大纲，列出还没出现的及各自触发词）
C. 按体验偏好核对当前状态：线索充足度 / 误导状态 / 隐藏环节 / 危险状态
D. 当前可走的路：2-4 条行动分支，每条注明耗时、风险、可能获得的信息
   （允许新开路径，但须标注【大纲外】并说明为什么现在出现）
E. 矛盾检查
不要推进剧情，只做整理。
```

## 7. 解析

### 7.1 大纲（宽松解析）

模型返回可能是：纯 YAML、```yaml 包裹、带客套话。

策略：
1. 提取 ```yaml ... ``` 代码块
2. 失败则从第一个 `1.` 或 `事件类型` 开始截取
3. 按行解析缩进层级（只支持 3 层：映射、列表、嵌套映射/列表）
4. 都失败 → 保留 `outlineRaw`，面板显示原文，提示手动编辑

不引入 YAML 库（无构建限制）。

### 7.2 盘点（结构化）

优先 `generateRaw({ prompt, jsonSchema })`，返回已解析对象。

风险：opencode.ai 接入点是否支持 JSON Schema 未知，**需实测**。不支持则退回宽松解析 + 正则提取字段。

## 8. 文件结构

```
src/event-outline/
├── manifest.json
├── index.js          入口，初始化、事件绑定
├── ui.js             悬浮窗 + 面板
├── prompt.js         OOC 词常量 + 偏好替换 + 拼装
├── context.js        上下文三层拼装
├── worldbook.js      世界书读写 + 锁 + 校验 + 快照
├── parse.js          大纲/盘点结果解析
├── store.js          事件卡读写、保留策略
└── adapters/
    └── shujuku.js    纪要读取
```

单文件也行（无构建），但 800+ 行容易乱，分成几个 `<script>` 由 index.js 动态注入或直接内联在一个文件里按段组织。

**决定**：单 `index.js`，内部用 `// ===== 模块名 =====` 分区，避免多文件加载顺序问题。预计 1,500–2,000 行。
