## 2. 被实测推翻的判断

这一节最重要。以下都是我一度以为对、查完源码发现错了的。

### 2.1 「用隐藏楼层就能既进上下文又不显示」——错

**我最初的判断**：把消息标 `is_system`，就能存下来但不渲染，同时模型还能看到，一举两得。

**实际**：`script.js:4496`

```js
let coreChat = chat.filter(x => !x.is_system || (canUseTools && ...));
```

`is_system` 消息被**完全排除出模型上下文**。它实现的是「存了但不给模型看」，和我们要的「给模型看但不显示」正好相反。

酒馆里不存在「渲染隐藏但进上下文」的官方机制。

**影响**：需求 2 的实现方式只能选 `generateRaw`。

### 2.2 「必须加 ignoreBudget，否则蓝灯会被预算截断」——错

**我最初的判断**：常量条目虽然不用关键词触发，但仍受预算限制（`:5061`），所以必须 `ignoreBudget: true`。

**机制判断是对的**，`world-info.js:5061` 确实会截断超预算条目。但我算预算时用错了上下文大小。

**实际数据**：

| 项 | 值 |
|---|---|
| `max_context`（旧字段） | 8192，**不生效** |
| `openai_max_context` | **2,000,000** |
| 实际预算（25%） | **约 49.25 万 token** |
| 现有 48 条蓝灯 | 约 10.8 万 token（17.3 万字符） |
| 余量 | **约 38.4 万 token** |

**结论反转**：预算宽裕得很，不需要 ignoreBudget。加上反而让条目脱离预算管理，以后调小预算时它不会跟着缩，是隐患。

**影响**：条目只设 `constant: true`；同时纠正了「30 万 context」这个记忆偏差。

### 2.3 「`/api/worldinfo/edit` 是增量接口」——错

**我最初的判断**：用 edit 接口做增量编辑，避免整本书重新序列化。

**实际**（`src/endpoints/worldinfo.js:134`）：它接收整本书对象，`writeFileAtomicSync` 整本覆盖写。**没有增量接口。**

**影响**：每次写入都是「整本读 → 改内存 → 整本发 → 整本落盘」。2.7MB 的书必须加全局写锁串行化，否则并发会互相覆盖。

好消息：实测整本读改写字节级无损（2,737,968 字节前后完全一致，127 个 EJS 条目零损失，uid 0–570 无断档）。

### 2.4 「shujuku 按聊天自动做对话隔离」——部分错

**我最初的猜测**：它既然实现了对话隔离，应该是按聊天 ID 自动分的。

**实际**（源码）：隔离靠用户手动设的隔离码。

```js
function getCurrentIsolationKey_ACU() {
    return Xd.dataIsolationEnabled && Xd.dataIsolationCode || "";
}
```

数据挂在 `TavernDB_ACU_IsolatedData[隔离键]` 下，历史码最多记 20 个。**没开隔离码时是空串**，同聊天内所有数据混在一起。

**为什么不能照抄**：隔离码是全插件一份全局设置，切码整个插件数据都换。它适合「同一聊天里切数据版本」，不适合「多条聊天各自独立」——还得手动记每条对话用哪个码，记错就串。

**影响**：我们改用 chatId 天然绑定 + 可选的聊天专属世界书双保险，零手动。

实测兰开斯特堡的隔离键确实是空串，印证了「没启用隔离码」。

### 2.5 「`generateRaw` 能吃到世界书蓝灯」——错

**我最初的判断**：既然蓝灯常驻了，`generateRaw` 应该也能读到。

**实际**：`generateRawData` 不调用 `getWorldInfoPrompt`，世界书、蓝灯、`setExtensionPrompt` 对它**统统无效**。

**影响**：必须自己拼三层上下文（事件卡 + 纪要 + 最近楼层）。

---

### 2.6 「可以直接调用 shujuku 内部的召回逻辑」——错

**危晓的问题**：既然 shujuku 已经有 LLM 召回，为什么还要我们自己走 API 精选？

**我最初的猜测**：它既然实现了对话隔离和召回，应该会暴露一些接口出来给别的扩展用。

**实际**：LLM 召回的执行函数 `runPlotTasksRuntime_ACU` 在打包产物里是 IIFE 私有闭包，检查四种暴露方式全部为 0 处：

- `window.runPlotTasksRuntime_ACU`
- `globalThis.runPlotTasksRuntime_ACU`
- 对象属性导出
- 斜杠命令注册

对外只暴露 `ACU_getCrossfireRollingDelta` 等几个零散全局，**没有任何召回入口**。

它和酒馆助手的关系也是单向的：它**用** `TavernHelper.generateRaw`，不对外提供自己的能力。

**但结论不是「只能自己扛」**。拆开看，精选动作只有「让模型点名」这一步需要花钱，而这一步就是一次 `generateRaw`。用它的内部实现，它自己也要调一次。**成本持平**，所以自己做不亏。

**顺带否决的取巧路**：蹭它的召回结果（等它注入上下文后捞出来）。放弃原因：时机耦合、格式不匹配、它一升级就断，代价最重只省一次调用。

**最终决定**：自己实现，照抄它的「概览清单 → 点名精读」思路。

额外收获：我们手里有事件卡状态（大纲/已触发节点），它的召回是通用盲猜，我们的召回是在「知道这个事件想考什么」的前提下做的，**准确度应该更高**。

**代价透明化**：盘点因此是两次 `generateRaw`（召回 + 盘点）。设置里可以关掉智能召回，退回直接给最近 N 条纪要，零额外调用。

---

### 2.7 「经典模式用老式存储，要单独适配」——错

**危晓的问题**：shujuku 的经典表格模式该怎么适配？

**我最初的猜测**：经典模式是「大总结归纳」，应该是另一套存储（`TavernDB_ACU_Data` / `TavernDB_ACU_SummaryData`），要单独写一个 adapter。

**实际**：存储只有两种，跟填表模式无关。

```js
function createProvider(t) {
  return "sqlite" === t ? new SqlTableService : new NativeTableServiceAdapter
}
```

四种填表模式共用同一套数据。`TavernDB_ACU_Data` / `SummaryData` / `IndependentData` 是**旧版本兼容字段**，`collectAllSheetDataFromMessage_ACU` 按 `IsolatedData` → `IndependentData` → `Data` → `SummaryData` 顺序兜底读取。

**实测佐证**：扫 VPS 上全部 4 个存档（仲夏夜、兰开斯特堡、石桥镇、异常女子高中），**全部只有 `IsolatedData`**，一个旧字段都没有。

**结论**：经典模式不需要单独 adapter，同一份代码读同一张表。区别只在召回策略——经典用「最近 N 条」（`classic.recentChronicleRows`，1–200），LLM 模式用「点名精读」。

**顺带发现的坑（很重要）**：shujuku 找纪要表是按名字 `"纪要表"` 找的，不是按 `sheet_ji_yao_biao` 这个 key。

```js
Object.values(t).find(t => "纪要表" === t?.name)
```

`sheet_ji_yao_biao` 只是兰开斯特那套模板的拼音命名，换卡换模板就变了，但名字不会变。我们如果按 key 写死，换模板时会**静默失效**——表还在，但读不到，退回纯楼层，且不报错。

所以 adapter 必须先按 `name === "纪要表"` 找，找不到再退回 key 匹配。

## 3. 危晓的裁决与理由

### 3.1 评审意见第 3 条：反向处理

原词写「D 项分支须对应推进路径节点，不得新开路径」。

危晓要求：**允许根据当前情况生成大纲里没有的新路径**，理由是「事件因为 user 参与，是有变化的」。

我的理解：原词防的是「凭空编造」，你要的是「合理演化」，两者不冲突。所以最终规则：

- 允许新开路径
- 但每条必须标注 `【大纲外】`
- 并写一句「为什么现在出现这条路径」

### 3.2 评审意见第 4 条：去掉「至少一名无条件」

危晓：「助力者的情况，不需要至少一名无条件，得根据实际判断。」

改为：每个助力者动机须各不相同，是否有条件/代价按实际判断。

### 3.3 世界书写进角色主世界书

危晓的推理：「扩展只会在对话中才会使用，这个时候角色世界书应该已经激活了。」

这个判断是对的，而且省掉了一个坑——不需要扩展自己去挂 `selected_world_info`。

代价是动核心数据（伊瑟利亚3.7，571 条 / 2.7MB），所以配套了六道防护（只增不改、写前快照、写后校验、全局锁、删除只删自己、原子写）。

### 3.4 需求 2 的措辞修正

危晓澄清：「我想的是不显示在正文里，避免影响观感。」

即约束是**视觉收口**，不是「永不进入对话」。我据此做了一轮技术路线比较，最终仍落在 `generateRaw`（因为 `is_system` 路堵死）。

### 3.5 盘点结果入库方式

危晓：「事件中的每次盘点出的内容，应该也要自动存入世界书。」

我提出改为**覆盖更新同一条**而不是新增，理由是蓝灯每轮都带，盘点五次就五条的话 token 翻几倍。危晓接受。

---

### 3.6 记忆来源做成可选项，默认自动

危晓：「记忆这块，我觉得可以在设置里有选项可以选择适配哪个记忆模块，默认是自动选择。」

我原本的设计是「适配器列表 + 固定优先级」，没有暴露选择。危晓这条改动把控制权交回用户，理由站得住：

- 换卡、换存档、换聊天时不用每次去改设置
- 多数对话没开 shujuku，手动固定会一直是「探测失败」状态

配套定的三条行为：

1. **面板始终显示当前实际用的是哪个**，读到多少条。不能让用户以为在用 shujuku，其实在纯楼层。
2. **手动指定探测失败时黄色提示 + 自动降级**，不报错不中断，给「切回自动」的按钮。
3. **不静默失败**。降级一定要看得见。

字段名从 `adapter` 改成 `source`，因为 `auto` 不是一个适配器而是一种选择策略。

## 4. 讨论过程中的次要发现

| 发现 | 说明 |
|---|---|
| 酒馆自带 memory 扩展 | `public/scripts/extensions/memory/index.js` 本身就用 `generateRaw` 做「不进正文的独立生成」，是最好的参照实现 |
| scene-map 被禁用 | `disabledExtensions` 里有 `third-party/scene-map`，不是故障 |
| shujuku 四种填表模式 | classic / vector / llm / crossfire，兰开斯特卷用 `llm` |
| 纪要表质量高 | 204 条纪要，每条带 AM 编码、时间跨度、≤30 字概览、240-480 字正文，比原始楼层精炼 |
| 兰开斯特堡规模 | 208 楼 / 37 楼带 shujuku 数据 / 17.8MB |
