## 1. 用户原话与诉求

> 「我觉得自己老实手动用这个 ooc 模板去自己手动打字选，输入，太麻烦了，想把这些功能作为一个扩展」

拆成三件事：

1. **不用再手抄**。OOC 词有两套，加起来约 2,000 字，每展开一个事件就要粘贴一遍、还要手改若干处偏好选项。
2. **不用再手选**。体验偏好有 6 组、共 25 个子项，每项都要手动把「按照委托等级自行设定」改成具体档位，还要把未选项删掉。
3. **不用再手动回贴**。盘点时要对照大纲逐条核对，人脑记不全，容易漏掉未触发节点和没被推翻的误导。

目标不是让 AI 替我写小说，而是**把「抄模板 + 改选项 + 核对大纲」这三件机械劳动从操作链里拿掉**，让讨论回归到「这次事件想要什么体验」。

## 2. 现状：手动流程与痛点

### 2.1 现在怎么操作

生成事件：
1. 打开 OOC 词文件，复制第一段（第 12–45 行）
2. 粘贴到对话输入框
3. 把 `【事件名】` 改成实际事件名
4. 逐条处理 6 组体验偏好：要么删掉不要的选项只留一个，要么保留整行让模型自选
5. 填 `额外要求`
6. 发送，等模型输出 YAML 大纲

事件进行中盘点：
1. 复制第二段（第 51–63 行）
2. 粘贴、发送
3. 自己拿输出对照当初那份 YAML 大纲，判断 C 项说得对不对

### 2.2 痛点分级

| 痛点 | 影响 | 严重度 |
|---|---|---|
| 两套词各 2,000 字左右，粘贴和改字是纯体力活 | 每次 2-3 分钟，且容易漏改某个子项 | 高 |
| 25 个子项手改，改错了模型就按错的档位设计 | 直接污染事件难度 | 高 |
| 大纲是模型输出的一条普通回复，会被上下文裁剪 | 事件开到一半大纲已经不在上下文里，盘点只能靠模型自己「回忆」 | 高 |
| 盘点时人工核对已触发/未触发节点 | 靠记忆，容易误判「卡关」 | 中 |
| 两段词的体验偏好可能前后不一致（OOC 词文件第 76 条评审意见） | 盘点按不同基准判断，结论失真 | 中 |
| 不同角色卡、不同故事线共用同一套词，但偏好应该按线区分 | 每次都要重新改一遍 | 中 |

其中**第 3 条是根因级问题**：不解决它，扩展只是把粘贴自动化了，模型该忘还是会忘。这也是 OOC 词文件第 71 条评审意见提出的方向（配一张事件状态卡，盘点读卡而不是读楼层）。

## 3. 范围

### 3.1 做什么（本期）

按危晓 5 条需求组织：

| 需求 | 落地 |
|---|---|
| 1. 可选酒馆已配 API 或单独 API，且**配置要能保存、方便切换**；默认跟随主连接 | 面板维护配置档，见 §6.6 |
| 2. OOC 与结果**不显示在正文**（避免影响观感） | 隔离生成或隐藏楼层，见 §4.5 |
| 3. 入口默认悬浮窗（可拖动、贴边吸附、可关），同时保留扩展菜单入口 | 双入口，见 §4.3 |
| 4. 生成内容持久化，避免长楼遗忘；**且同一角色卡下多条对话互不影响** | 写角色主世界书 + 聊天隔离设计，见 §4.4、§4.6 |
| 5. 生成内容在扩展内可见 | 面板展示大纲正文、tracker、历次盘点结果 |
| 6. 历史事件保留可配（完结多留、废弃少留） | 见 §4.9 |
| 7. 每次盘点结果自动存入世界书 | 覆盖更新同一条目，见 §4.8 |

具体功能：

- 「开新事件」：填事件名、选偏好、填额外要求 → 拼大纲 prompt → **独立生成** → 解析 → 存事件卡 + 写世界书蓝灯条目
- 「盘点」：读事件卡 + 近期楼层 → 拼盘点 prompt → **独立生成**（jsonSchema）→ 结果只在面板展示 → 可一键更新世界书条目
- 「查看/编辑」：面板内看大纲正文与 tracker，可手动改
- 「收尾 / 暂停」：删或禁用世界书条目，事件卡留档

### 3.2 不做什么（明确排除）

- 不自动推进剧情、不代替你回消息——扩展只做结构生成，正文仍是模型在正常对话里写
- **不在正文区渲染任何 OOC 或生成结果**——需求 2，但楼层是否物理存在取决于 §4.5 实测选型
- 不改角色卡、不改你现有世界书里**任何已有条目**（只追加自己前缀的新条目）
- 不生成正文——大纲和盘点只做结构
- 不做多线管理（一本世界书对一条线）
- 不碰 OOC 词原文文件——那是存档，改它要你另外授权

### 3.3 评审意见裁决（2026-10-30 危晓已定）

OOC 词文件第 67–76 行有 7 条评审意见，明确标注「尚未改动原文」。扩展一旦落地，等于把这套词**工程化**了。裁决结果：

| # | 评审意见 | 裁决 | 落地方式 |
|---|---|---|---|
| 1 | 大纲配事件状态卡，盘点读卡不读楼层 | **采纳** | 事件状态卡同时进 chatMetadata 与世界书蓝灯条目（需求 4） |
| 2 | 大纲强制输出「推进所需最少信息节点编号」 | **采纳** | 大纲 prompt 加一条硬性输出要求 |
| 3 | D 项分支须对应推进路径节点，不得新开路径 | **不采纳，反向处理** | 你明确要求：允许根据当前情况生成最初大纲里没有的新路径。理由是你本人参与后剧情会变，硬性锁死反而失真。改为「分支可以新开，但须标注『大纲外新路径』并说明触发原因」 |
| 4 | 助力者动机各不相同，至少一名无条件 | **部分采纳** | 去掉「至少一名无条件」的硬性要求，改为「每个助力者动机须各不相同，是否有条件/代价按实际判断」。不再强加无罪推定 |
| 5 | 误导的反向证据须是节点清单里的条目并注编号 | **采纳** | 大纲 schema 里误导项带 `refute_by: [节点编号]` |
| 6 | 两段词偏好保持一致，或只在大纲定、盘点读大纲 | **采纳** | 偏好只存事件卡一份，盘点时读卡，不重复询问 |
| 7 | 幕后方改为固定键值 `reveal: forbidden` | **采纳** | schema 固定字段，不让模型自由扩写 |

关于第 3 条，多说一句：这条改动很关键。原词写「不得新开路径」是为了防止模型乱编，但你的实际需求是「事件是因为 user 参与才有变化的」——这跟原词的初衷其实不冲突，原词防的是「凭空编造」，你要的是「合理演化」。所以最终规则定为：

- 盘点 D 项允许给大纲外的新分支
- 但每条新分支必须标注 `【大纲外】` 并写一句「为什么现在出现这条路径」
- 原有节点照旧只能用清单内的

这样既保留你的自由度，又不会让模型无中生有。

注意：这 7 条裁决等于**在扩展内部出一版改良词**，而存档文件里的原文保持不变。两者会分叉，在 `docs/` 里记清楚「线上跑的哪一版」。

## 4. 功能设计

### 4.1 事件卡（核心数据结构）

事件卡是这套扩展的地基。生成大纲后，把模型返回的 YAML 解析出来存成结构化数据：

```json
{
  "id": "evt-20261030-1430",
  "name": "石桥镇失踪案",
  "status": "active",            // active 进行中 / completed 已完结 / abandoned 已废弃
  "createdAt": "2026-10-30T14:30:00+08:00",
  "closedAt": null,
  "chatId": "伊瑟利亚 - 2026-10-29",
  "worldBook": "伊瑟利亚3.7",     // 条目写进了哪本书
  "entryUid": 42,                // 对应世界书条目 uid
  "prefs": {
    "commissionLevel": "auto",
    "clueSufficiency": "够用",
    "misleadingStrength": "轻度",
    "hiddenSegments": "auto",
    "infoPresentation": "间接",
    "lethality": "低",
    "failureConsequence": "受伤或被俘",
    "tolerance": "中",
    "threatSource": "敌对角色",
    "timePressure": "隐藏",
    "timeDuration": "适中",
    "timeoutConsequence": "损失机会或信息",
    "procrastinationCost": "无",
    "extra": "偏重对话博弈"
  },
  "outline": { /* 模型返回的 YAML 原样解析结果 */ },
  "tracker": {
    "triggeredNodes": [],
    "refutedMisleads": [],
    "offPathBranches": [],       // 评审意见 3 裁决：大纲外新路径
    "manualNotes": ""
  },
  "inventories": [               // 每次盘点的完整记录（需求 7）
    {
      "at": "2026-10-30T15:20:00+08:00",
      "round": 1,
      "raw": "……模型返回原文……",
      "parsed": { /* jsonSchema 或宽松解析结果 */ },
      "committedToBook": true    // 是否已写入世界书
    }
  ]
}
```

要点：
- `status` 支持完结/废弃两种收尾方式（需求 5）
- `inventories` 保存每次盘点的完整原始输出，不只存最后一次——这样能回看事件的推进轨迹
- `worldBook` + `entryUid` 记录条目落在哪，收尾时精确删除
- `tracker` 是人工可编辑的进度标记。**不自动猜测**哪个节点触发了；模型说触发了，你点一下确认，防止模型自己记错

### 4.2 四种操作

**开新事件**
1. 点按钮 → 面板弹出
2. 填事件名（必填）、额外要求（可空）
3. 选 6 组偏好，默认「根据当前情况自行设定」（需求 3 新增档位，见 §4.7）
4. 点「生成大纲」→ 直接生成（不预览，需求 6 已定）
5. 等模型返回 → 尝试解析 YAML → 成功则展示摘要并保存；失败则原样展示，提示手动复制
6. 保存为事件卡（`status: active`）+ 写世界书蓝灯条目

**盘点**
1. 点「盘点」→ 需要当前有 `active` 事件卡，没有就提示先建
2. 扩展拼出盘点 OOC，把事件卡的大纲摘要 + tracker 状态一并发起生成
3. 结果展示在扩展面板里（不落正文）
4. **自动把这次盘点结果写回世界书条目**（需求 7，见 §4.8）
5. 面板上列出未触发节点，方便你点选标记

**收尾（完结 / 废弃）**
1. 点「收尾」→ 选「完结」或「废弃」
2. 删掉世界书里那条常驻条目（`status` 改掉，`entryUid` 记录保留供追溯）
3. 事件卡留在 chatMetadata 里，`status` 变成 `completed` 或 `abandoned`
4. 按保留策略自动清理超出上限的旧卡（见 §4.9）

**查看 / 查看历史**
- 当前事件：展示大纲正文、tracker 勾选、历次盘点记录
- 历史事件：按状态分组列出往期事件卡，可展开看当时的大纲和盘点，但不能继续盘点

### 4.3 界面

**双入口，悬浮窗为默认**（2026-10-30 危晓定）：

1. **悬浮窗按钮（默认开启）**
   - 初始位置：左侧，纵向居中偏上
   - 可拖动，拖到窗口某侧边缘**自动吸附**进去（贴边后半隐，鼠标移上去再展开，参考 scene-map 的 `PEEK` 做法）
   - 位置记在 localStorage，下次打开还原
   - 可在设置里关掉悬浮窗，只用菜单入口
2. **扩展菜单入口（常驻）**
   - 酒馆左侧竖排扩展按钮区（`#extensionsMenu`），点击打开同一面板
   - 悬浮窗关了也能用，是兜底入口

两个入口打开的是同一个工作面板。风格延续 scene-map 的暖色系（金/米黄）。

移动端：手机屏窄，悬浮窗默认位置要靠边且小，吸附后不遮挡输入框；扩展菜单是折叠列表，按钮文字要能单独辨识。

### 4.4 多聊天隔离（你的核心诉求）

你要求：同角色卡下的两条对话不能互相影响。

**先说结论：这件事分两层，一层天然成立，一层必须专门处理。**

| 层 | 内容 | 现状 |
|---|---|---|
| 事件卡本身 | 存在 chatMetadata 里 | 天然隔离，切聊天就切，不串 |
| 世界书条目 | 写进角色主世界书（全局文件） | **会串**，必须处理 |

#### 4.4.1 参考实现：shujuku 是怎么做的

你说在用那个插件实现了对话隔离，我扒了它的源码（9MB 打包产物），核心就一行：

```js
function getCurrentIsolationKey_ACU() {
    return Xd.dataIsolationEnabled && Xd.dataIsolationCode || "";
}
```

要点：

- 隔离靠**用户手动设置的隔离码**（`dataIsolationCode`），不是自动按聊天生成
- 数据挂在每条 AI 消息的 `TavernDB_ACU_IsolatedData[隔离键]` 字段下，同一个聊天里可以用不同隔离码存多份数据
- 历史隔离码最多记 20 个（`isolationCodeList`），可在设置里切换
- **没开隔离码时隔离键是空串**，同聊天内所有数据落在同一份

它还额外做了很多我们不需要的东西：版本化 checkpoint、回放、完整性校验、向量索引。那是数据库插件的重量级需求，我们只要「不串」这一件事。

#### 4.4.2 我们的方案：两条独立机制

因为世界书是全局文件、内容不随聊天走，光靠「存聊天里」不够。所以采用**双保险**：

**机制一：sha 级引用校验（主）**

世界书条目内容里第一行固定写入：

```
〔事件大纲｜chatId=<当前聊天ID>｜book=<世界书名>｜v1〕
```

模型读到这条会先看到身份标记。同时扩展侧：

- 打开面板时校验当前 `chatId` 是否等于条目里的 `chatId`
- 不等就不显示该事件卡，并提示「这属于另一条对话的大纲」
- 扫描世界书时只认 `▸事件｜` 前缀且 `chatId` 匹配的条目

**机制二：聊天专属世界书（可选，推荐开启）**

对**同卡多条对话**这种真正持续并存的情况，机制一只能防误读，防不住两条对话都写了蓝灯条目、模型同时看到两条。

所以给一个开关：**「本聊天专用一本书」**

- 开启后，第一次建事件时自动复制一份角色主世界书到 `事件大纲-<聊天名>`，挂到这条聊天的世界书激活列表
- 之后这条对话的条目都写进这本书，其他对话看不见
- 关掉就是写回角色主世界书，用机制一防串

这个开关默认**关**（符合你「挂已激活角色世界书」的原意），但当你在同一张卡下开了第二条对话时，扩展会提示建议开启。

#### 4.4.3 为什么不照抄 shujuku 的隔离码

shujuku 的隔离码是**全插件一份全局设置**，切码后整个插件的数据都跟着换。它适合「同一聊天里切换数据版本」，不适合「多条聊天各自独立」——因为你还得手动记得每条聊天该用哪个码，记错就串了。

我们要的是**零手动**的隔离：聊天 ID 就是隔离键，天然唯一、不需要用户维护。这比隔离码更省心。

#### 4.4.4 兜底：串了怎么发现、怎么修

- 面板顶部常显示当前绑定的世界书和条目 chatId，一眼能核对
- 提供「自检」按钮：扫世界书里所有 `▸事件｜` 条目，列出哪些 chatId 对不上
- 一键清理不匹配条目（只删自己前缀的）

### 4.5 OOC 与生成结果的显示规则（需求第 2 条）

你的原话：「不显示在正文里，避免影响观感」。所以约束的本质是**视觉收口**，不是「永不进入对话」：

- **OOC 请求不渲染在正文**：不在聊天区占楼、不留痕
- **生成结果不渲染在正文**：大纲和盘点结果只在扩展面板里看
- 正文区保持干净，只有你自己写的话和模型的正常回复

两名候选实现，采哪个取决于实测：

| 方式 | 做法 | 观感 | 上下文的完整性 |
|---|---|---|---|
| **完全隔离开**（原方案） | `generateRaw` 独立请求，结果不落聊天，扩展自己拼楼层进 prompt | 最干净 | 要自己补前情，有损 |
| **隐藏楼层**（备选） | 照常走聊天生成，但消息带 `is_system`/隐藏标记，不渲染 | 正文看不见，但楼层存在 | 完整，模型真看得到 |

两者都能满足「不显示在正文」。差别在于：隔离方案干净但要自己喂上下文；隐藏楼层方案上下文天然完整，但要确认酒馆 1.19.0 有可靠的「存而不显」手段，且这类楼层在存档里仍可被翻到、也会占 chatMetadata。

实测时两条都试，优先隐藏楼层（上下文完整性更高），不行再退回隔离开。


### 4.6 生成内容的持久化（需求第 4 条）

「事件卡存 chatMetadata」只能解决「扩展自己能看到」，**解决不了模型在长楼里遗忘**——因为 chatMetadata 不会进入模型上下文。

你的判断是对的：**扩展只会在聊天中打开，此时角色世界书已经激活**。源码确认 `characters[chid].data.extensions.world`（`world-info.js:5686`）就是角色主世界书，聊天时自动激活，不需要扩展再去挂载。所以方案定为：

- **条目直接写进角色主世界书**（如 `伊瑟利亚3.7`），不新建书，也不动激活列表
- 条目名前缀 `▸事件｜`，方便识别和批量清理

技术上有三个坑必须处理：

1. **预算截断**：常量条目（`constant: true` 蓝灯）在 `:4893` 直接激活，但 `:5061` 仍受预算限制，超了就丢。所以必须同时设 `ignoreBudget: true`。
2. **写的是你的核心世界书**。这是你要的效果——条目和设定在同一本书里，随卡激活——但意味着**扩展在动伊瑟利亚3.7 这种核心数据**。风险控制见下。
3. **内容要压缩**。`ignoreBudget` 等于无上限，每轮都带。控制在 800–1,500 字（约 600–1,100 token），占 30 万 context 的 0.2%–0.4%。

写核心世界书的风险控制（必须全部做到）：

| 措施 | 说明 |
|---|---|
| 只增不改 | 写入时只追加 `▸事件｜` 前缀的新条目，**绝不改动任何已有条目** |
| 改动前快照 | 每次写入前把整本书的 JSON 存一份到 chatMetadata（`event_outline.wiSnapshot.<时间戳>`），可一键还原 |
| 前置备份 | 首次写入前提示并落实到 `运维/VPS/酒馆/备份` |
| 删除只删自己 | 清理时只删 `▸事件｜` 前缀的条目，绝不整本覆盖 |
| 写入校验 | 写完回读一次，比对条目数只增不减、已有条目内容未变；不一致立即中止并告警 |
| 用 edit 接口不用 save | 走 `/api/worldinfo/edit` 的增量编辑，避免整本书重新序列化引发字段丢失 |

**生命周期**：生成大纲时写入 → 每次盘点后更新自己那一条 → 事件结束点「收尾」删除该条目。

**下线方式**：点「收尾」删条目，或面板一键暂停（`disable` 置 true，保留内容不删）。

**保底方案**：如果实测发现往核心世界书写会引发兼容问题（比如某些卡的数据结构），退回「新建 `事件大纲-<线名>` 专用书 + 扩展自己挂激活列表」。这个 fallback 在开工验证阶段决定，不预先实施。

### 4.7 偏好档位：新增「根据当前情况自行设定」（需求第 3 条）

原词里每个子项的第一档是「按照委托等级或具体事件难度自行设定」。你觉得不够用，因为：

- 原档是「先定事件难度，再倒推各子项」——但难度本身也是要设的，容易绕圈
- 你想要的是「让模型看当下的剧情氛围，自己判断该松还是该紧」

所以新增一档 **「根据当前情况自行设定」**，与原有三档并列：

| 档位 | 含义 |
|---|---|
| **根据当前情况自行设定**（新增，且为默认） | 模型读当前剧情与上下文，自行判断该子项取哪个强度 |
| 按照委托等级或具体事件难度自行设定 | 原档：先看难度等级，再定档 |
| 各具体档位 | 原词里的「充足 / 够用 / 稀缺」等 |

实现：
- 6 组 25 个子项，每个下拉的第一项都是这个新档
- 新档默认选中
- 拼 prompt 时，「根据当前情况自行设定」被替换成 `根据当前剧情情况自行设定`，其余各档照原文替换

这个改动和在原词存档的关系：属于新增选项，**不改动原词已列出的任何一档的措辞**。

### 4.8 盘点结果自动写入世界书（需求第 7 条）

你说：事件中每次盘点出的内容，应该也自动存入世界书。

方案：**盘点结果是「更新同一条目」，不是「新建一条」**。

原因：如果每次盘点都新加一条，一个事件盘点五次就五条蓝灯，每轮全带上，token 直接翻几倍。所以：

1. 盘点完成 → 解析结果
2. 取出事件卡里当前的世界书条目内容
3. 用盘点结果更新其中「已确认信息 / 未触发节点 / 当前危险状态 / 已推翻的误导」几块
4. 保留大纲的结构性信息（核心真相、节点编号清单）
5. 写回同一条目

条目内容结构（压缩版，控制在 800–1,500 字）：

```
〔事件大纲｜chatId=xxx｜v3｜更新于 10-30 15:20〕
事件：石桥镇失踪案（进行中，第 3 次盘点）
核心真相：〔禁止透露〕镇长之子实为……

节点清单（1-8）：
 1 物证·水井旁的鞋 —— 已触发
 2 证言·守夜人 —— 已触发
 3 环境·旧仓库 —— 未触发（触发词：仓库/旧栈房）
 …
推理所需最少节点：2 与 5
误导：A（镇长隐瞒）—— 已被节点 4 推翻
当前威胁：镇长家仆，高风险节点为 6，失败后果受伤
容错：已消耗 1/3
大纲外新路径：【大纲外】因为你救了守夜人，现在可走「守夜人引荐」路线
```

每次盘点覆盖写入，`v` 号递增，`更新于` 跟着变。历史记录留在事件卡的 `inventories` 数组里，不占世界书。

### 4.9 历史事件保留策略（需求第 5 条）

你要：完结的多保留，废弃的少留，数量可设。

| 状态 | 默认保留 | 可设置范围 |
|---|---|---|
| `completed` 已完结 | 20 张 | 1–100 |
| `abandoned` 已废弃 | 3 张 | 1–50 |
| `active` 进行中 | 不限（正常只有 0–1 张） | 固定的 |

清理时机：每次点「收尾」后自动跑一次。按 `closedAt` 倒序保留，超出的从最旧的删起。

两个保护：
- 清理只动 chatMetadata 里的事件卡，不碰世界书、不碰聊天正文
- 删之前给个提示「将清理 N 张超出上限的历史卡」，可在设置里关掉提示

设置存在 `extension_settings`，跟 API 配置档放一起，三端同步。

## 5. 技术方案

### 5.1 技术底座（已实测确认）

VPS 上酒馆是 **SillyTavern 1.19.0**（容器 `sillytavern`，镜像 `ghcr.io/sillytavern/sillytavern:1.19.0`），`/opt/tavern/extensions` 挂到容器内 `public/scripts/extensions/third-party`。

已装的 6 个扩展：JS-Slash-Runner（酒馆助手 4.11.3）、ST-BaiBai-Book、ST-Prompt-Template、SillyTavern-Pathweaver、scene-map（自己写的）、shujuku（龙血玄黄数据库 1.3）。

前端扩展只需 `manifest.json` + `index.js`，不重启容器，硬刷生效，删目录即回滚。

**已确认可用的 API**（来自 `public/scripts/st-context.js` 的 `getContext()` 返回值）：

| 用途 | API |
|---|---|
| 读聊天 | `ctx.chat`（数组）、`ctx.chatId` |
| 读 chat metadata | `ctx.chatMetadata` |
| 存 chat metadata | `ctx.saveMetadata()` / `ctx.saveMetadataDebounced()` |
| 触发一次生成 | `ctx.generate(type, options)`、`ctx.generateQuietPrompt(...)`、`ctx.generateRaw({prompt, systemPrompt, jsonSchema, ...})` |
| 强制结构化输出 | `generateRaw` / `generateQuietPrompt` 的 `jsonSchema` 参数：传入后会要求模型按 schema 返回，成功时函数**直接返回已解析的对象**（`script.js` 第 4000 与 4122 行实测确认） |
| 直接塞一条消息 | `ctx.addOneMessage(mes, opts)`、`ctx.saveReply(...)` |
| 系统消息 | `ctx.sendSystemMessage(text)` |
| 注入隐藏提示 | `ctx.setExtensionPrompt(key, value, position, depth)` |
| 请求头（含 CSRF） | `ctx.getRequestHeaders()` |
| 事件 | `ctx.eventSource.on(ctx.eventTypes.CHAT_CHANGED / MESSAGE_RECEIVED, fn)` |

**关键设计问题**：OOC 要以**用户消息**身份进入对话，模型才会当成你的 OOC 指令。「写入并发送」和「不写入、只拿结果」是两条不同的路，见 §6。

### 5.2 存储选型对比

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| `chatMetadata`（聊天文件内） | 跟着聊天走，三端同步，重启不丢，天然按聊天隔离 | 写聊天文件，与「只读扩展」的保守原则有冲突 | **推荐** |
| `extension_settings`（settings.json） | 官方推荐位置 | 全局一份，多聊天会串；改 settings.json 有覆盖风险 | 次选，只存 UI 偏好 |
| localStorage | 最简单，scope 安全 | 只在本浏览器，手机/工位/家里不同步 | 只存按钮位置这类 UI 状态 |
| 独立文件（走服务端 API） | 完全隔离 | 需要写后端接口，跨出前端扩展的范围 | 不做 |

推荐组合：**事件卡进 chatMetadata，UI 偏好进 localStorage**。

注意：`chatMetadata` 有大小限制（酒馆会把它序列化进聊天文件）。一份大纲 YAML + tracker 大概几 KB，几十个事件也就几百 KB，可接受，但要在实现时设个上限并提示。

## 6. 关键设计与已决事项

### 6.1 OOC 怎么进对话 —— 已定：不渲染在正文

你的第 2 条需求（不显示在正文，避免影响观感）排除了「当用户消息发出去让用户看见」这条路。两个候选：

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 写进输入框 | 扩展填输入框，你按发送 | 否，会留在正文 |
| B. 当用户消息直发 | `addOneMessage` + 正常发送 | 否，会留在正文 |
| **C. 独立生成** | `generateRaw` / `generateQuietPrompt`，结果自己接住渲染到面板 | **备选，需补上下文** |
| **D. 隐藏楼层** | 走正常聊天生成，消息存但不渲染 | **首选，待实测** |

优先 D：上下文天然完整，模型真能看到前情和世界书，只是不在界面上显示。如果 1.19.0 没有可靠的「存而不显」手段，退到 C。

### 6.2 生成怎么拿到剧情上下文（本期核心）

如果走 C，`generateRaw` 是独立请求，只发你给它的 prompt，要自己补前情：

| 路径 | 做法 | 取舍 |
|---|---|---|
| 甲：拼聊天记录进 prompt | 取最近 N 楼（按 token 预算）拼进 prompt | 简单直接，但要自己控 token 和选楼 |
| 乙：世界书蓝灯常驻 | 事件状态已常驻，`generateRaw` 是否走世界书扫描需实测 | 若生效，最省事 |
| 丙：extension prompt 注入 | `setExtensionPrompt` | 只影响正常生成，对静默生成无效 |

走 C 时用 **甲 + 乙 双保险**。走 D 则不需要这一步——这正是 D 更优的原因。

### 6.3 生成大纲后怎么解析 —— 已定：分两条路

**生成大纲：宽松解析**
- prompt 里要求 YAML
- 返回后：先试 ` ```yaml ``` ` 提取，再试裸 YAML 解析，失败则原样展示存档
- 自己写一个够用的解析器（无构建限制，不能用 js-yaml），只解析嵌套到 3 层的映射和列表

**盘点：强解析**
- 传 `jsonSchema`，返回直接是对象
- 好处：能按字段精准更新 tracker、精确比对节点
- 风险：需确认 opencode.ai 接入点支持 JSON Schema 模式；不支持就退回宽松解析
- 注意：走 D（隐藏楼层）时 jsonSchema 可能不适用，届时盘点也用宽松解析 + 字段正则提取

### 6.4 世界书蓝灯常驻的已知坑（需求 4 详解）

源码实测（1.19.0）：

- 常量条目在 `world-info.js:4893` 直接激活，无需关键词 ✅
- 但 `:5061` 处受预算限制：`textToScanTokens + newContent >= budget` 即停止，**超出预算的条目被丢弃**
- 预算默认 `world_info_budget = 25`（百分比），30 万 context 约 7.5 万 token
- 解药：条目字段 `ignoreBudget: true`（`:3852` 有对应 UI 开关），勾上后不参与预算检查
- **写哪本书**：`characters[chid].data.extensions.world`（`:5686`）即角色主世界书，聊天时自动激活，扩展不用管激活列表

所以扩展写条目时必须显式设：

```js
{
  constant: true,       // 蓝灯
  ignoreBudget: true,   // 不被预算截断
  disable: false,
  key: [],              // 常量为空
  content: '……压缩后的事件状态……',
  comment: '▸事件｜事件名｜自动生成勿手改',
  position: 0,
  depth: 4,
  order: 100
}
```

**关于激活列表**：既然写进角色主世界书（聊天时天然激活），扩展**不需要**动 `selected_world_info` 或 `chat_metadata.world_info`。这比原方案少一个坑，也是你这条建议的价值。

**关于全局文件**：角色主世界书是全局文件，一本可能被多个角色共用。写入的条目只按当前聊天/is 事件区分，不假设「一本书只服务一条线」。

**第四点**：用了 `ignoreBudget` 就等于无上限占用，所以内容必须压缩到 800–1,500 字（约 600–1,100 token），占 30 万 context 的 0.2%–0.4%。这也是为什么大纲要摘要化而非原样存 YAML。

**下线方式**：点「收尾」删条目，或面板一键暂停（`disable` 置 true，保留内容）。

### 6.5 扩展会写聊天数据与世界书，与「只读」原则冲突

交接文档写过「自己写的扩展默认只读，不写回聊天与世界书」，原因是与卡内 MVU/stat_data 抢状态的经典坑。本扩展按需求 4 必须写：

- **写 chatMetadata 的自有命名空间**（`chatMetadata.event_outline`），只写自己的键，不碰 `stat_data`、`MVU`
- **往角色主世界书追加一条自己的条目**（不改任何已有条目）——这是你定的方案，风险高于新建专用书，控制措施见 §4.6

风险控制：
- 条目名统一前缀 `▸事件｜`，一眼能认出是扩展写的
- 写入前后做差异校验，已有条目零改动才放行
- 每次写前留整本快照到 chatMetadata
- 删除只删自己前缀的条目
- 动数据前照旧备份（`运维/VPS/酒馆/备份`）

### 6.6 API 选择与配置保存（需求第 1 条）

`generateRawData({ api })` 与 `generateQuietPrompt` 都支持传 `api`，不传则用 `main_api`。你要的是**能保存配置、方便切换**，所以做成配置档：

| 项 | 设计 |
|---|---|
| 配置档 | 可存多套：名字、api 类型、endpoint、model、key（掩码显示） |
| 内置一组「跟随酒馆主连接」 | 不传 api，用 `main_api`，换模型自动跟着走 |
| 单独配置档 | 面板里选一套，生成时把 api/endpoint/model/key 传入 |
| 切换方式 | 面板顶部下拉，选完立即生效，下次打开记住上次的 |
| 生成时独立于正常对话 | 剧情正文仍用酒馆主连接，大纲/盘点用你选的这套——互不影响 |

存储位置：**`extension_settings`（服务端 settings.json 里的扩展命名字段）**，不是 localStorage。

- 好处：三端同步、换浏览器还在、key 不明文躺在浏览器里
- 注意：改 settings.json 有被运行时副本覆盖的风险（AGENTS.md 红线）。扩展必须走酒馆的 `saveSettingsDebounced()` 正规路径，不能自己直接改文件

key 的保护：
- 界面只显示 `sk-****abcd` 掩码
- 不进日志、不进 console、不进仓库
- 如果以后要导出配置，掩码化后才导出

其他注意：你的接入点挂了 opencode.ai 补丁，补丁只对 custom 端点 + opencode.ai host 生效；单独配 opencode 时能吃到补丁，配别的 endpoint 时不吃。
